Projectile ballistics with quadratic drag

Projectile ballistics with quadratic drag

A projectile lives by Newton's second law: gravity pulls it down, the air slows and pushes it sideways. For quadratic drag there is no analytic solution — the trajectory is integrated numerically, most often with RK4.

differential equationsRunge–KuttaCCD
01 Essence

Drag grows with the square of speed: Fd = ½ρCdA|v|v. At low speeds the linear term matters, but for bullets, shells and balls the quadratic term dominates. Wind enters through the relative velocity v − w: the air pushes the projectile along its own motion instead of merely slowing it down.

Explicit Euler (“position += velocity · dt”) accumulates error and visibly breaks apart at high speeds. RK4 evaluates the derivative four times per step and gives a local error of O(dt⁵) at the price of four evaluations — the best compromise for gameplay. For higher accuracy use adaptive stepping (RK45) or Verlet-like schemes.

Aiming is the inverse problem: find the angle or the fuse time. Solve it by simulating forward with a bisection on the angle, by range tables, or with an iterative ballistic solver. Above roughly 300 m/s a continuous collision test (swept sphere / raycast) is mandatory, otherwise the projectile tunnels through walls between frames.

the mathematical model
m·dv/dt = m·g − ½·ρ·Cd·A·|v − w|·(v − w)
ρ — air density, Cd — drag coefficient, A — cross-section area, w — wind velocity. Acceleration: a = g − (k/m)·|v−w|·(v−w), where k = ½ρCdA.
02 How to build it
  1. Set the initial position, velocity, mass, Cd, area and wind vector.
  2. Each sub-step, evaluate the four slopes k₁…k₄ of the coupled (p, v) system.
  3. Update velocity and position with the weighted sum: y += dt/6 · (k₁ + 2k₂ + 2k₃ + k₄).
  4. Test the segment p → p′ against colliders (continuous collision detection).
  5. For trajectory prediction, run the same function in a shadow simulation with no effects and no audio.
03 Working code
Python 
import math

def deriv(state, wind, g, k_over_m):
    px, py, vx, vy = state
    rx, ry = vx - wind[0], vy - wind[1]
    s = math.hypot(rx, ry)
    ax = g[0] - k_over_m * s * rx
    ay = g[1] - k_over_m * s * ry
    return (vx, vy, ax, ay)

def rk4(state, dt, wind, g, k_over_m):
    k1 = deriv(state, wind, g, k_over_m)
    k2 = deriv([s + dt/2*d for s, d in zip(state, k1)], wind, g, k_over_m)
    k3 = deriv([s + dt/2*d for s, d in zip(state, k2)], wind, g, k_over_m)
    k4 = deriv([s + dt*d   for s, d in zip(state, k3)], wind, g, k_over_m)
    return [s + dt/6*(a + 2*b + 2*c + d_)
            for s, a, b, c, d_ in zip(state, k1, k2, k3, k4)]

# state = [x, y, vx, vy]; g = (0, -9.81)
# at 120 Hz: state = rk4(state, 1/120, wind=(3, 0), g=(0, -9.81), k_over_m=0.0009)
04 Computational complexity
Time
O(1) per step, 4 acceleration evaluations
Memory
O(1)
In practice
Predicting N steps is O(N). At 120 Hz a step costs microseconds.
05 Where people usually get it wrong
  • Explicit Euler at dt = 1/30 and 800 m/s drifts the projectile by metres — use RK4 or sub-steps.
  • Tie the integration step to the fixed physics tick and interpolate the render, or the trajectory floats at different frame rates.
  • Cd depends on the Mach number: a tabulated curve gives a plausible transonic dip, a single constant does not.
  • Point collisions tunnel — sweep a capsule or sphere along the whole movement segment.

Stat-driven critical hit system

Stat-driven critical hit system

A crit chance is not a constant but a function of a stat. The logit model keeps the probability inside (0, 1), while the Poisson distribution answers a different question: how many crits happen over a series of hits.

Poisson distributionlogit modelPRD
01 Essence

The logit links a linear combination of stats to a probability: p = 1 / (1 + e−(β₀ + β₁·stat)). The coefficient β₁ sets the price of one stat point in log-odds, so the curve never escapes 100 % and scales to any level. The inverse, logit(p) = ln(p/(1−p)), is a designer's tool: +1 to a stat gives a constant increase in log-odds.

The number of crits over n independent rolls is binomial. For large n and small p it is approximated by a Poisson: P(k) = λᵏe−λ/k!, where λ = n·p. That lets you estimate “how many crits will I land in 20 seconds of combat” and budget damage without simulating.

Players feel long dry spells badly even though they are statistically normal. Competitive games therefore use pseudo-random distribution (PRD): the chance grows after each miss and resets after a hit. The mean stays as advertised, the variance drops, and the feeling becomes honest.

the mathematical model
p(stat) = σ(β₀ + β₁·stat), P(k) = λᵏ·e−λ / k!, λ = n·p
σ(z) = 1/(1+e−z) is the sigmoid. For PRD: pₙ = min(1, C·n) after n misses; pick C numerically so that E[attempts] = 1/p.
02 How to build it
  1. Collect a base chance and express stat contributions in log-odds, not in percentages.
  2. Clamp the probability to a sane ceiling (usually 75–90 %) and add a floor.
  3. Roll the RNG once per hit; apply the crit multiplier after armour.
  4. For combo mechanics, evaluate λ = n·p and check the burst against the damage budget.
  5. If players complain about bad luck, enable PRD and re-measure average DPS on a playtest.
03 Working code
Python 
import math, random

def crit_chance(stat, b0=-2.2, b1=0.08):
    # b0 sets the base chance, b1 the strength of one stat point
    return 1.0 / (1.0 + math.exp(-(b0 + b1 * stat)))

class PRD:
    """Pseudo-random distribution: reduces the variance of streaks."""
    def __init__(self, p, constant=0.3):
        self.p = p
        self.constant = constant   # tuned with Monte Carlo
        self.failures = 0

    def roll(self, rng=random):
        chance = min(1.0, self.constant * self.p * (self.failures + 1) ** 1.5)
        if rng.random() < chance:
            self.failures = 0
            return True
        self.failures += 1
        return False

p = crit_chance(stat=42)          # ~0.66 with these betas
prd = PRD(p=0.25)
04 Computational complexity
Time
O(1) per hit
Memory
O(1)
In practice
PRD stores only a failure counter — one variable per character or weapon.
05 Where people usually get it wrong
  • “Five hits without a crit means one is coming” is a player illusion; PRD honestly raises the chance, the raw probability does not change.
  • Clipping the probability at 1.0 without recomputing the damage budget turns late game into a crit lottery.
  • Adding or multiplying crit multipliers has to be a conscious choice — mixing them creates unexpected DPS explosions.
  • The RNG must be server-side and logged, otherwise crit chance is the first thing to be exploited.

Dynamic economy pricing

Dynamic economy pricing

A price is a signal about scarcity. The model is Walrasian price finding: excess demand pushes the price up, excess supply pushes it down, and elasticity sets how strong the reaction is.

differential equationsgame theoryelasticity
01 Essence

The classic dynamics: dp/dt = k·(D(p) − S(p)), where D and S are demand and supply. Modelling them as powers, D(p) = D₀·(p/p₀)−ε, gives a convenient dimensionless elasticity ε: the percentage change in demand per percent change in price. For a game economy, stability matters more than accuracy: the price must stay positive and must not oscillate around equilibrium forever.

The second layer is strategic behaviour. NPC traders, auctions and resellers form a game with a Nash equilibrium; if one player can buy out an entire resource and spike the price, the server needs countermeasures: purchase limits, regional markets, a resale tax, instant arbitrage fees. A pure formula without institutions breaks against player behaviour.

In practice prices update on a market tick (every 30–300 seconds), smoothed with an EMA and capped by a relative step. The logarithmic reaction p′ = p·ek·excess guarantees positivity and makes growth and fall equally noticeable.

the mathematical model
excess = (D − S) / max(D, S), p′ = p · ek·excess, p ← p + α(p′ − p)
k — market reaction speed, α — smoothing. An EMA filter damps oscillations and blunts manipulation by a single large order.
02 How to build it
  1. Identify sources and sinks of each good: drops, crafting, consumption, taxes, spoilage.
  2. Build D(p) and S(p) with elasticities; give NPC traders a reserve price.
  3. Run the market tick less often than the game tick so prices do not jitter.
  4. Cap the change per tick (e.g. ±10 %) and set absolute floors and ceilings.
  5. Log volume, price and trade count: inflation is visible in a price index, not in one currency.
03 Working code
Python 
import math

def market_tick(price, demand, supply, k=0.15, alpha=0.25,
                floor=0.2, ceiling=5.0):
    denom = max(demand, supply, 1e-6)
    excess = (demand - supply) / denom          # in [-1, 1]
    target = price * math.exp(k * excess)       # always > 0
    new_price = price + (target - price) * alpha
    return max(price * floor, min(price * ceiling, new_price))

# example: a shortage pushes the price up smoothly, without oscillation
p = 100.0
for _ in range(5):
    p = market_tick(p, demand=120, supply=80)
    print(round(p, 2))

Time
O(1) per good per tick
Memory
O(#goods)
In practice
With player inventories it is O(#orders); use heaps or sorting for the order book.
05 Where people usually get it wrong
  • A large k makes the price oscillate around equilibrium — the market rings and players cannot react.
  • Without sinks the currency inflates: prices rise not from scarcity but because there is more money.
  • Arbitrage between regions must be either forbidden or turned into gameplay with logistics and risk.
  • Hidden NPC dampeners (“infinite demand”) destroy the point of trading — prefer explicit reserves and quotas.

Spline paths and arc-length parameterization

Spline paths and arc-length parameterization

A spline defines a smooth curve through control points. The classic trap: the parameter t is not proportional to the distance travelled — without an arc-length table, cameras and characters speed up on tight bends.

Bézier curvesCatmull–Romarc length
01 Essence

The cubic Bézier curve: B(t) = (1−t)³P₀ + 3(1−t)²tP₁ + 3(1−t)t²P₂ + t³P₃. It stays inside the convex hull of its control points and is C²-smooth inside a segment, but segment joints need explicit stitching. Catmull–Rom passes through every point and gives C¹ continuity for free — which is why it is the favourite for tracks, cameras and patrols.

The parameter t is uniform in the formula but not along the arc. Moving an object as p(t + Δt) makes it visibly accelerate around corners. The fix is an arc-length table: sample the curve, accumulate distances, normalise, and find t by bisection for the desired distance. Integrating |B′(t)| analytically is possible but a lookup table is simpler and accurate enough (256–1024 samples).

For gameplay what matters is constant speed, a curvature limit (turning radius) and no self-intersections. Check the curvature κ = |x′y″ − y′x″| / (x′² + y′²)3/2: too sharp a turn breaks both the camera and the physics.

the mathematical model
B(t) = Σ C(3,i)·(1−t)3−i·ti·Pᵢ, s(t) = ∫₀ᵗ |B′(u)| du
Catmull–Rom: B(t) = ½[(2P₁) + (−P₀+P₂)t + (2P₀−5P₁+4P₂−P₃)t² + (−P₀+3P₁−3P₂+P₃)t³].
02 How to build it
  1. Pick the control points and the spline type: Bézier for authored shapes, Catmull–Rom to pass through points.
  2. Build the arc-length LUT: N samples with accumulated distances.
  3. For a distance s find t by bisection in the LUT (O(log N)).
  4. Orient the object along the tangent B′(t) and derive the roll from curvature and speed.
  5. Clamp the step s so the object does not cut corners on tight bends.
03 Working code
Python 
import bisect, math

def bezier(p0, p1, p2, p3, t):
    u = 1 - t
    return tuple(u**3*a + 3*u*u*t*b + 3*u*t*t*c + t**3*d
                 for a, b, c, d in zip(p0, p1, p2, p3))

def build_lut(points, samples=512):
    pts = [bezier(*points, i/(samples-1)) for i in range(samples)]
    acc, lut = [0.0], [0.0]
    for a, b in zip(pts, pts[1:]):
        acc.append(acc[-1] + math.dist(a, b))
    total = acc[-1]
    return pts, [d / total for d in acc]   # normalised lengths

def t_at_distance(lut, s):
    s = min(max(s, 0.0), 1.0)
    i = bisect.bisect_left(lut, s)
    return (i - 1) / (len(lut) - 1)        # linear interpolation of t
04 Computational complexity
Time
O(N) to build, O(log N) per sample
Memory
O(N)
In practice
A static track builds the LUT once; a dynamic one recomputes it as points change.
05 Where people usually get it wrong
  • Moving along the raw t gives uneven speed — always reparameterise by arc length.
  • Catmull–Rom can loop between points; check curvature and limit the tension.
  • A sparse LUT causes visible jerks on long curves; use 1024+ samples for racing tracks or adaptive subdivision.
  • Damp the camera follow, otherwise turns look twitchy.

Quantum state mechanics

Quantum state mechanics

A quantum state is a vector of amplitudes, and measurement is a probabilistic transition to one of the basis states. In a game this yields an “uncertain until observed” mechanic backed by honest mathematics.

linear algebradensity matricessuperposition
01 Essence

A qubit is described by |ψ⟩ = α|0⟩ + β|1⟩, where |α|² + |β|² = 1. Before measurement the object “is in superposition”: a door is both open and closed, an enemy exists in two corridors. Measurement yields 0 with probability |α|² and 1 with probability |β|², after which the state collapses.

Mixed states (when there is classical uncertainty) are described by a density matrix ρ = Σ pᵢ|ψᵢ⟩⟨ψᵢ|. Gates are unitary matrices: Hadamard creates superposition, CNOT entangles two qubits. For n qubits the vector holds 2ⁿ amplitudes — which is why a full quantum simulator inside a game is limited to roughly 10–20 “qubits”.

The key difference from magic: an unknown state cannot be cloned (no-cloning), entanglement cannot carry information faster than light (no-signaling), and save/load must preserve the distribution — otherwise players reload until they get the outcome they want. Fix the RNG seed inside the world state, and design probabilistic mechanics so that every outcome is playable.

the mathematical model
|ψ⟩ = α|0⟩ + β|1⟩, |α|² + |β|² = 1, P(0) = |α|²
Hadamard gate: H = 1/√2 · [[1, 1], [1, −1]]. For two qubits the basis is |00⟩, |01⟩, |10⟩, |11⟩; CNOT flips the second when the first is 1.
02 How to build it
  1. Choose the representation: pure states (n ≤ ~12) or density matrices (noise, decoherence).
  2. Define unitary gates and their visual counterparts in the world.
  3. On “measurement”, roll the RNG with the amplitude probabilities and store the outcome in the object state.
  4. Sync the seed between clients and server for deterministic multiplayer.
  5. Saves store amplitudes/matrices, not the observed outcome — otherwise the mechanic loses its point.
03 Working code
Python 
import math, random

# |psi> = a|0> + b|1>; a state is a list of complex amplitudes
def hadamard(state):
    a, b = state
    r = 1 / math.sqrt(2)
    return [r * (a + b), r * (a - b)]

def measure(state, rng=random):
    p0 = abs(state[0]) ** 2
    outcome = 0 if rng.random() < p0 else 1
    # after measurement the state collapses
    collapsed = [1.0, 0.0] if outcome == 0 else [0.0, 1.0]
    return outcome, collapsed

psi = [1.0, 0.0]          # |0>
psi = hadamard(psi)        # (|0> + |1>) / sqrt(2)
print(measure(psi, random.Random(42)))

Time
O(2ⁿ) per state, O(4ⁿ) per gate (naive)
Memory
O(2ⁿ) amplitudes
In practice

05 Where people usually get it wrong
  • Storing the “observed” state destroys the superposition and devalues the mechanic.
  • Reloading until the desired outcome appears means the player lacks control over the probabilities — offer a choice or a pity mechanic.
  • Do not explain physics to the player; explain rules: “while nobody is looking, the object is in two places”.
  • Using entanglement as instant communication is a design error, not a physics nuance.

4X strategy AI (utility, MCTS, influence maps)

4X strategy AI (utility, MCTS, influence maps)

Strategic AI splits a decision into situation assessment, option generation and choice. Utility AI is faster and more predictable, MCTS is stronger in tactics, and influence maps connect the map to those decisions.

utility AIMCTS/UCTdecision trees
01 Essence

Utility AI scores every action as score = Σ wᵢ·fᵢ(context), where fᵢ are normalised factors (food need, enemy proximity, gold reserve). The choice can be greedy or sampled with a softmax and a temperature: a high temperature gives variety, a low one gives determinism. Weights are tuned by simulations and telemetry, not by eye.

For tactical fights, use MCTS with UCT: a* = argmax Q(s,a) + c·√(ln N(s)/N(s,a)). The tree grows towards promising branches and rollouts are replaced by a light heuristic. On large maps plain MCTS is expensive, so it is combined with abstraction: unit groups, regions, and “strategic layers” running every N seconds.

Influence maps are a convolution of the map by the influence radius of units and buildings. They answer cheap questions: “where are we strong”, “where is it safe to move”, “where will the opponent open a front”. The fog of war matters: the AI must decide on the last known information, otherwise it reads as cheating and the game stops being fun.

the mathematical model
score(action) = Σ wᵢ·fᵢ(ctx), P(a) = escore(a)/τ / Σ escore(b)/τ
UCT: Q(s,a) + c·√(ln N(s) / N(s,a)). Q — mean reward, N — visit count, c balances exploration and exploitation.
02 How to build it
  1. Collect the context: resources, threats, goals, fog of war, diplomacy.
  2. Describe 10–30 actions with their factors; normalise the factors into [0, 1].
  3. Split the layers: strategy (every 5–30 s), tactics (every 0.5–2 s), micro (every tick).
  4. Add hysteresis and cooldowns so the AI does not flip plans every tick.
  5. Validate behaviour on replays: metrics like “time to react”, “units lost”, “map share”.
03 Working code
Python 
import math

def softmax_pick(actions, context, weights, temperature=0.35):
    scores = {}
    for name, feature_fn in actions.items():
        feats = feature_fn(context)          # {"food_need": 0.8, "threat": 0.2, ...}
        scores[name] = sum(weights[name].get(k, 0.0) * v for k, v in feats.items())
    m = max(scores.values())
    exp = {k: math.exp((v - m) / temperature) for k, v in scores.items()}
    z = sum(exp.values())
    return {k: v / z for k, v in exp.items()}

# actions: expand, build_farm, build_barracks, attack, defend
# features(ctx) -> {food_need, threat, gold, enemy_weakness}

Time
Utility O(#actions·#factors), MCTS O(iterations·depth)
Memory
O(tree + map)
In practice

05 Where people usually get it wrong
  • An AI that sees through the fog of war reads as cheating — keep a separate per-faction memory.
  • Switching decisions too often makes the army jitter; use hysteresis and a minimum hold time.
  • Utility weights overfit to one player strategy — test against several styles and on several maps.
  • MCTS without abstraction hits a combinatorial wall at 20–30 units.

Emotional NPC model (PAD + appraisal)

Emotional NPC model (PAD + appraisal)

An NPC emotion is a point in “pleasure – arousal – dominance” space that decays smoothly and is shifted by events. Such a model produces continuous reactions instead of a set of scripted animations.

PAD modelOCCclustering
01 Essence

The PAD model (Pleasure, Arousal, Dominance) describes mood as a three-dimensional vector. Events are evaluated with the OCC scheme: desirability, probability, expectedness, control. “An enemy stole the food” drops Pleasure hard, raises Arousal and lowers Dominance; “I won” raises all three with high control.

The dynamics are E′ = E·λ + Σ wᵢ·eventᵢ, with decay towards the base personality and clamping into [−1, 1]. Characters differ by λ (cooling speed), their base point and their appraisal weights. It is cheap, interpretable and easy for a designer to tune from a table.

The raw vector is useless for animation — it has to be discretised. Clustering (k-means over labelled emotions: joy, fear, anger, sadness) yields the state that selects an animation tree and a line of dialogue. Hysteresis and a minimum transition duration prevent flickering; strong emotions suppress weak ones but do not erase them instantly.

the mathematical model
E ∈ [−1,1]³ = (P, A, D), E′ = clamp(λ·E + Σ wᵢ·eventᵢ)
λ ≈ 0.9–0.99 per game tick. Classify an emotion by the nearest PAD centroid or by per-axis thresholds.
02 How to build it
  1. Define the NPC character: base PAD point, cooling speed, sensitivity to events.
  2. Describe events through appraisal features: desirability, control, expectedness, blame/merit.
  3. Update the emotion on events and let it drift back to the baseline.
  4. Classify the state into animations and lines with hysteresis.
  5. Expose the emotion through behaviour: distance, aggression, willingness to trade — the player must be able to read it.

import math

DECAY = 0.96

Adaptive difficulty (skill estimation + RL)

Adaptive difficulty (skill estimation + RL)

The goal of adaptive difficulty is to hold the player in the flow between boredom and frustration. Difficulty is chosen from an estimate of skill and behaviour, not from a single health bar.

Q-learningBayesian networksbandit
01 Essence

First you have to estimate the player. The simplest version is an Elo/TrueSkill-like rating based on duel outcomes. A more informative one is a Bayesian network over features: accuracy, reaction time, death count, use of cover, pace of progress. The posterior skill distribution is updated after every fight rather than “by account level”.

Choosing the difficulty is a multi-armed bandit: enemy parameters (damage, aggression, reinforcement count) are the arms, the reward is closeness to a target success rate (say 60–70 % wins) plus retention. Thompson sampling or ε-greedy explore the space without breaking the feeling of fairness.

Inside a fight, Q-learning applies: Q(s,a) ← Q(s,a) + α[r + γ·max Q(s′,a′) − Q(s,a)]. The reward encourages tense but winnable fights and punishes instant deaths and meat-grinders. The adaptation has to stay invisible: players must never see enemies “giving up”, or the victory loses its value.

the mathematical model
Q(s,a) ← Q(s,a) + α·[r + γ·maxa′Q(s′,a′) − Q(s,a)]
α — learning rate, γ — discount. For DDA the reward is r = −|winrate − target| − λ·(deaths / time).
02 How to build it
  1. Choose a success metric: win rate, fight duration, deaths per checkpoint, resource spend.
  2. Estimate the player's skill Bayesianly; do not mix it with gear progress.
  3. Limit the adaptation space to 3–5 parameters so the balance stays under control.
  4. Change parameters in steps with a delay: abrupt tuning reads as cheating.
  5. Verify that the game stays fun at low skill and does not turn into a punching bag simulator at high skill.

Procedural dialogue (Markov → transformers)

Procedural dialogue (Markov → transformers)

Dialogue can be generated on three levels: a Markov chain for cheap variation, a grammar for controlled meaning, and an LLM for free-form speech. Games almost always need a hybrid with hard constraints.

Markov chainstransformersgrammars
01 Essence

A first-order Markov chain stores transition probabilities between words: P(wₜ | wₜ₋₁). Training is a matter of counting pairs, generation is a random walk over the graph. It is cheap and produces plausible noise, but the coherence is short: after 10–15 words the model has forgotten the beginning. For names and short lines that is often enough.

The modern approach is a transformer with attention: Attention(Q,K,V) = softmax(QKᵀ/√dk)V. The model accounts for the whole context, but it needs tokens, memory and latency. Games use small local models (1–8B parameters), KV caching, streaming generation and length limits. Quality jumps when the model is given structured context: who speaks, the relationship, known facts, the current quest.

The production pattern: an authored dialogue graph defines branches and consequences, while the LLM rephrases lines inside a node under constraints (tone, length, forbidden topics, world facts). Validating answers, falling back to a template and logging are mandatory — generative text without guardrails breaks lore and ratings.

the mathematical model
P(w₁…wₙ) = Π P(wₜ | wₜ₋₁), Attention(Q,K,V) = softmax(QKᵀ/√dk)·V
For trigrams: P(wₜ | wₜ₋₂, wₜ₋₁). Temperature T divides the logits before the softmax: higher T is more varied, lower T more stable.
02 How to build it
  1. Define the boundaries of freedom: which names, lines and branches may be generated.
  2. Collect a corpus in the character's voice, or define a grammar with slots.
  3. Add state: relationships, memory of events, current goal — otherwise the dialogue is meaningless.
  4. Limit the length and check facts against a knowledge base; fall back to a template on failure.
  5. Log and moderate the output, especially in multiplayer and UGC.

Flocking / boids and crowd steering

Flocking / boids and crowd steering

Three simple rules — keep distance, match heading, approach the centre — produce a convincing flock. The secret is not the rules but the spatial index and the clamping of forces.

flocking theoryboidsspatial hash
01 Essence

Reynolds' boids: separation (push away from close neighbours), alignment (match the heading of neighbours), cohesion (steer towards the centre of the group). Each rule yields a vector; they are blended with weights and clamped by magnitude. Different radii per rule matter: separation short, cohesion long.

Naive all-pairs is O(n²) — for 500 units that is 250 000 checks per frame. A spatial hash (grid with a cell around the perception radius) brings it down to O(n·k), where k is the average neighbour count. For thousands of agents, run the rules in a compute shader or use flow fields for long-range movement.

On top of boids sit steering behaviours: obstacle avoidance, pursuit, formation keeping, queuing at a door. Clamping maximum force and speed, plus priorities (separation beats cohesion), prevent jitter and density explosions. For deterministic multiplayer the update must run on a fixed tick and must not depend on iteration order.

the mathematical model
v ← clamp(v + Σ wᵢ·steerᵢ·dt, vmax), steersep = Σ (p − pⱼ)/|p − pⱼ|²
Neighbouring is usually limited by radius and field of view (270°, say), otherwise the flock “sees” behind itself.
02 How to build it
  1. Rebuild the spatial hash from agent positions once per tick.
  2. For each agent gather neighbours inside the perception radius.
  3. Compute the three forces, normalise them, blend with weights; separation gets priority.
  4. Clamp acceleration and speed; add damping so the flock settles down.
  5. Add obstacles and leaders (a flow field or a goal), otherwise the flock circles in place.

import math

def neighbors_hash(agents, cell):
    grid = {}
    for a in agents:
        key = (int(a["x"] // cell), int(a["y"] // cell))
        grid.setdefault(key, []).append(a)
    return grid

def steer(b, grid, cell, R=60):
    sep_x = sep_y = ali_x = ali_y = coh_x = coh_y = 0.0
    n = 0
    cx, cy = int(b["x"] // cell), int(b["y"] // cell)
    for gx in (cx-1, cx, cx+1):
        for gy in (cy-1, cy, cy+1):
            for o in grid.get((gx, gy), ()):
                if o is b: continue
                dx, dy = o["x"]-b["x"], o["y"]-b["y"]
                d2 = dx*dx + dy*dy
                if d2 > R*R or d2 == 0: continue
                sep_x -= dx / d2; sep_y -= dy / d2
                ali_x += o["vx"]; ali_y += o["vy"]
                coh_x += o["x"];  coh_y += o["y"]
                n += 1
    if not n: return (0.0, 0.0)
    return (1.6*sep_x + 0.9*(ali_x/n - b["vx"]) + 0.004*(coh_x/n - b["x"]),
            1.6*sep_y + 0.9*(ali_y/n - b["vy"]) + 0.004*(coh_y/n - b["y"]))

  • Agents jitter around obstacles without smoothing and hysteresis — add damping.

Procedural terrain with fBm and erosion

Procedural terrain with fBm and erosion

A landscape is a sum of noise octaves: large shapes make mountains, small ones make rocks. Realism arrives when you add erosion, biomes and passability constraints on top of the noise.

Perlin noisefractalserosion
01 Essence

Fractal Brownian motion: h(x) = Σ aᵢ·noise(fᵢ·x), where every octave doubles the frequency and halves the amplitude. Perlin gives gradient noise without the blockiness of value noise, and the ridged variant (1 − |noise|)² creates mountain ridges. Domain warping — displacing coordinates with another noise — adds winding valleys and unusually beautiful shapes.

Raw noise looks fluffy but does not look like land. Hydraulic erosion models water droplets: a droplet rolls along the gradient, erodes the ground, carries sediment and deposits it in the low areas. A few hundred thousand droplets per map produce valleys, alluvial fans and river beds. For real-time use, pre-bake the erosion into a texture and use it as a mask.

Biomes follow temperature and humidity: height plus latitude gives temperature, distance to water plus wind gives humidity. Then the rules: desert, forest, tundra, swamp. Gameplay validation matters: the map needs connected traversable routes, starting zones with resources and natural borders. Chunks are generated with LOD, and noise is sampled in world coordinates — otherwise seams appear at the borders.

the mathematical model
fBm(x) = Σi=0O−1 gaini·noise(x·lacunarityi)
Typical: O = 4–8 octaves, lacunarity = 2, gain = 0.5. Ridged: (1 − |noise|)² sharpens the ridges.
02 How to build it
  1. Generate the base fBm height in world coordinates from a seed.
  2. Add mountain ridges with ridged noise and warping for valleys.
  3. Run erosion (offline or on the GPU) and keep the sediment map.
  4. Compute temperature and humidity and classify biomes.
  5. Check connectivity and starting zones; build the navigation mesh and LOD chunks.

import math

def fbm(x, y, noise2, octaves=6, lacunarity=2.0, gain=0.5):
    amp, freq = 1.0, 1.0
    total = norm = 0.0
    for _ in range(octaves):
        total += amp * noise2(x * freq, y * freq)
        norm += amp
        amp *= gain
        freq *= lacunarity
    return total / norm          # normalised to [-1, 1]

def terrain_height(x, y, noise2, sea=0.0):
    base = fbm(x, y, noise2) * 0.5 + 0.5
    ridge = 1.0 - abs(fbm(x * 2.1, y * 2.1, noise2, 4))
    h = base * 0.75 + ridge * 0.25
    return max(0.0, h - sea) ** 1.6   # raised mountains, flat lowlands

Dynamic global illumination

Dynamic global illumination

Global illumination is an integral over all directions that accounts for light bounced off other surfaces. In real time it is approximated: with probes, with ray tracing plus denoising, or with baked lightmaps.

rendering equationradiositypath tracingDDGI
01 Essence

The rendering equation: Lo(x, ωo) = Le + ∫ fr(x, ωi, ωo)·Li(x, ωi)·cosθi dωi. It is recursive: Li is the light leaving other surfaces. It has analytic solutions only for simple scenes; numerically it is estimated by Monte Carlo sampling.

Path tracing estimates the integral as the mean over rays: L ≈ (1/N)·Σ f·L·cosθ / pdf. For a Lambertian material f = albedo/π and pdf = cosθ/π, so the factors cancel to albedo — which is why the estimator is so elegant. The problem is noise: removing it needs a denoiser (SVGF, OIDN) and temporal accumulation with reprojection.

Real-time alternatives: baked lightmaps and irradiance probes for static light, DDGI — a grid of probes updated with rays and spherical harmonics, screen-space GI (cheap, but blind to what is off-screen), and Lumen-style hybrids with an SDF scene. Radiosity solves a linear system for diffuse surfaces and is still used for baking.

the mathematical model
Lo = Le + ∫Ω fr·Li·cosθi dωi
For a diffuse surface: Lo = Le + (albedo/π)·∫ Li cosθ dω. Radiosity iterations converge to the solution of the form-factor system.
02 How to build it
  1. Set the budget: baked light, probes, or a full ray tracer.
  2. Separate direct and indirect light: direct via shadows and maps, indirect via probes or rays.
  3. For path tracing add next-event estimation (NEE) and a denoiser.
  4. For DDGI update probes in portions across frames and store SH coefficients.
  5. Watch for light leaks and shadow bias; tune the bias carefully.

import math

def basis(n):
    helper = (0.0, 1.0, 0.0) if abs(n[1]) < 0.99 else (1.0, 0.0, 0.0)
    t = normalize(cross(helper, n))
    return t, cross(n, t)

def cosine_hemisphere(n, rng):
    u1, u2 = rng.random(), rng.random()
    r, phi = math.sqrt(u1), 2 * math.pi * u2
    tangent, bitangent = basis(n)      # orthonormal frame around n
    cos_t, sin_t = math.cos(phi), math.sin(phi)
    return tuple(tangent[i] * (r * cos_t) + bitangent[i] * (r * sin_t)
                 + n[i] * math.sqrt(max(0.0, 1.0 - u1)) for i in range(3))

def radiance(ray, depth, scene, rng):
    hit = scene.intersect(ray)
    if hit is None:
        return scene.sky(ray.direction)
    if depth == 0:
        return hit.emission
    wi = cosine_hemisphere(hit.normal, rng)
    # f_r = albedo/pi, pdf = cos(theta)/pi  =>  f_r*cos(theta)/pdf = albedo
    return hit.emission + hit.albedo * radiance(
        hit.spawn(wi), depth - 1, scene, rng)

Destruction: stress, Voronoi, rigid bodies

Destruction: stress, Voronoi, rigid bodies

Destruction is a comparison of stress against material strength. To keep it playable, fragments are almost always prepared in advance (Voronoi) and the runtime only decides which piece to break off.

elasticityFEMVoronoi
01 Essence

Stress σ = F/A, strain ε = ΔL/L, Hooke's law σ = E·ε. When the stress exceeds the ultimate strength, the material cracks. For brittle objects (glass, concrete) not only the force but the direction of the impact matters; for metals, plastic deformation matters. Full FEM in real time is far too expensive, so physics is simplified to rigid bodies and pre-cut fragments.

Voronoi cutting: generate points inside the volume, then each point claims the nearest volume. The result is a mosaic of convex shards that fit together exactly. Several levels of detail are baked in advance (big pieces → small ones) and the right one is activated on impact. Connectivity is checked by walking the neighbour graph: detached pieces must fly away rather than hang in the air.

The runtime budget: cap the number of active rigid bodies, sleep them once they settle, merge small shards into decals and dust, and use LOD for distant debris. In multiplayer, destruction has to be server-authoritative or deterministic from a seed — otherwise clients see different walls.

the mathematical model
σ = E·ε, break when σ > σmax, Eimpact = ½mv²
For brittle materials add a maximum shear stress criterion (Mohr–Coulomb) and cracks along the impact direction.
02 How to build it
  1. Split the object into structural and decorative parts; give the structural ones a strength.
  2. Pre-cut the object into Voronoi shards with 2–3 levels of detail.
  3. Build a neighbour graph to check connectivity after an impact.
  4. On impact, compare energy/stress with the threshold and activate the shards.
  5. Cap the number of active bodies and replace small debris with particles and decals.

Water rendering with FFT waves and SPH

Water rendering with FFT waves and SPH

Water in a game is two different algorithms: an ocean surface (sum of waves, FFT, reflections) and a volume/interaction model (SPH or a height field). Mixing both in one system is expensive, so they are almost always separated.

Navier–StokesSPHFFT waves
01 Essence

Navier–Stokes for an incompressible fluid: ∂u/∂t + (u·∇)u = −∇p/ρ + ν∇²u + f, ∇·u = 0. Solving it directly on a grid in real time only works for small volumes. For an ocean, the spectral approach wins: a sum of sinusoids with the deep-water dispersion relation ω² = g·k, where k is the wavenumber. An FFT over a Phillips spectrum gives a 256×256 height and normal map in milliseconds on a GPU.

SPH (Smoothed Particle Hydrodynamics) represents the fluid as particles with a smoothing kernel W: density ρᵢ = Σ mⱼW(rᵢⱼ, h), pressure from the equation of state p = k(ρ − ρ₀). Pressure and viscosity forces push the particles apart; boundaries are handled with penalty forces. SPH is great for splashes, waterfalls and puddles, but it needs sub-steps and yields a noisy surface that has to be reconstructed with marching cubes or screen-space fluids.

Rendering water: Fresnel reflection F(θ) = F₀ + (1−F₀)(1−cosθ)⁵, refraction distorted by the normal, depth absorption following Beer's law (colour depends on distance), foam driven by a height/speed threshold, and caustics as a projected texture. Without Fresnel and depth fog, water looks like blue plastic.

the mathematical model
∂u/∂t + (u·∇)u = −∇p/ρ + ν∇²u + f, ∇·u = 0, ω² = g·k
SPH: ρᵢ = Σⱼ mⱼ·W(|rᵢ−rⱼ|, h), pᵢ = k·(ρᵢ − ρ₀). Fresnel: F = F₀ + (1−F₀)(1−cosθ)⁵.
02 How to build it
  1. Choose the model: FFT waves for open ocean, a height field for rivers, SPH for splashes and volumes.
  2. For the ocean, generate the spectrum, run the inverse FFT for heights and normals, and add fine ripple with a normal map.
  3. For SPH tune h, mass, stiffness and the number of sub-steps; stabilise the pressure (PCISPH/DFSPH).
  4. Render with Fresnel, refraction and depth absorption; add foam from the velocity.
  5. Sync the wave phases over the network or keep them purely visual on the client.

// Gerstner wave: vertical and horizontal displacement
vec3 gerstner(vec2 p, vec2 dir, float steepness, float wavelength,
              float speed, float t, out vec3 normal)
{
    float k = 6.28318 / wavelength;
    float c = sqrt(9.81 / k);          // phase speed
    float f = k * (dot(dir, p) - c * speed * t);
    float a = steepness / k;
    normal = vec3(-dir.x * steepness * cos(f),
                  1.0 - steepness * sin(f),
                  -dir.y * steepness * cos(f));
    return vec3(dir.x * a * cos(f), a * sin(f), dir.y * a * cos(f));
}

Volumetric clouds and ray marching

Volumetric clouds and ray marching

A cloud is a density field in a volume. A ray steps through it accumulating scattered light; the key to quality is the density function (fBm with erosion) and a cheap lighting approximation.

ray marchingdensity functionsBeer–Lambert
01 Essence

Density comes from 3D noise: ρ(x) = smoothstep(threshold, threshold + w, fbm(x)) with a height gradient and a “weather map” on the ground. To make clouds look fluffy you subtract higher-frequency noise from the base shape (erosion) — cheaper and prettier than one noise with many octaves.

Ray marching takes N steps along the ray, evaluates density at each step and accumulates transmittance with the Beer–Lambert law T = exp(−∫σ·ds). Lighting is estimated with a “cheap” second march towards the sun (6–8 steps) and a Henyey–Greenstein phase function for the silver lining. A full sun march at every step is far too expensive, so precomputed light maps or a depth-based approximation are used instead.

Optimisations: empty-space skipping through a mip pyramid of the density, jittering the start offset to hide banding, temporal accumulation with reprojection, and blue-noise dithering. Clouds are the classic case where 32 steps with good noise look better than 128 steps with bad noise.

the mathematical model
T = exp(−∫ σt(x) ds), L = ∫ σs(x)·T(x)·Lsun·phase(θ) ds
HG phase: P(θ) = (1−g²) / (4π(1 + g² − 2g·cosθ)3/2), g ≈ 0.6–0.8 for forward scattering.
02 How to build it
  1. Generate a 3D density texture: base shape + erosion noise, with height falloff.
  2. Build a mip pyramid of the density for empty-space skipping.
  3. Ray march in the shader with a dithered start and an adaptive step size.
  4. Estimate lighting with a short march towards the sun or from a light map.
  5. Accumulate across frames with reprojection and reset the history when the camera moves.

float density(vec3 p) {
    float base = texture(noise3D, p * 0.5).r;

    float shape = smoothstep(0.45, 0.75, base - erosion * 0.25);

                          (1.0 - smoothstep(0.7, 1.0, p.y));

Client-side prediction and interpolation

Client-side prediction and interpolation

The network brings latency, so the client shows movement earlier than the server does: it predicts its own actions locally and interpolates everyone else's. Divergence is fixed with a soft correction, not a teleport.

Kalman filterextrapolationrollback
01 Essence

The classic scheme: input → the client applies movement immediately (prediction) → the server recomputes authoritatively → the client compares and corrects. Keep a ring buffer of inputs and states; when a server snapshot arrives, resimulate from the last confirmed tick (rollback). That is how Quake/Source and most shooters work.

Other players are rendered with interpolation and a delay of roughly 100–150 ms: show the past, but smoothly. Extrapolation (continuing the current velocity) helps when packets are lost, but produces “rubber” opponents at sharp direction changes. A Kalman filter gives an optimal estimate of position and velocity given measurement noise: x̂ₖ = x̂ₖ⁻ + K(zₖ − Hx̂ₖ⁻), where K depends on the ratio of process and measurement noise.

Smoothing the error: the position and angle offset decay exponentially (usually over 100–200 ms) rather than snapping. For shooting you need lag compensation — the server rewinds hits to the client's firing moment, otherwise at 80 ms of ping you simply cannot hit moving targets. All of this requires synchronised clocks and a stable tick.

the mathematical model
x̂ₖ = x̂ₖ⁻ + K·(zₖ − H·x̂ₖ⁻), K = P⁻Hᵀ(HP⁻Hᵀ + R)⁻¹
Model: xₖ = F·xₖ₋₁ + w, zₖ = H·xₖ + v. For position+velocity F = [[1, dt], [0, 1]], H = [1, 0].
02 How to build it
  1. Fix the server tick (say 30–60 Hz) and the snapshot protocol.
  2. The client applies its own input immediately and stores (tick, input, state) in a buffer.
  3. On a snapshot, find the confirmed tick, correct the state and resimulate the pending inputs.
  4. Render remote players with a delay and interpolation; enable extrapolation only for packet loss.
  5. Smooth the visual error and disable prediction for teleports and death.

Anti-cheat: statistical anomaly detection

Anti-cheat: statistical anomaly detection

Anti-cheat is a layered system: an authoritative server, statistical anomaly detection, client-side checks and a ban economy. Z-score catches outliers, but you must be careful with false positives.

z-scoreanomaliestrust
01 Essence

Basic hygiene first: the server never trusts the client for position, damage or resources. The client sends input, the server sends the result. For particularly sensitive data, run the fog of war on the server: the client never receives enemy positions it cannot see. That removes a whole class of wallhacks without any statistics at all.

Statistics: for every player, track metrics such as headshot ratio, reaction time, accuracy at long range, and the distribution of aim angles. The z-score z = (x − μ)/σ shows how far a metric has drifted from the population. But among millions of players you will find dozens of honest outliers, so use robust estimators (median/MAD), combinations of metrics and Bayesian priors rather than a single threshold.

Detection without a reaction is worthless: review replays of suspicious matches, shadow ban suspects into a separate pool, ban in waves, and provide appeals. Client-side anti-cheats (signatures, memory integrity) raise the price of cheating but give no guarantees; kernel-level solutions are a privacy question of their own. The success metric is not “we caught everyone” but “playing honestly is comfortable”.

the mathematical model
z = (x − μ)/σ, robust: z′ = 0.6745·(x − median)/MAD
MAD = median(|x − median(x)|). |z′| > 3.5 is the classic outlier criterion for normal data.
02 How to build it
  1. Close the basic holes: server authority, input validation, server-side fog of war.
  2. Collect telemetry: hits, latencies, angles, movement, economy — tagged per match.
  3. Build robust distributions per skill bucket rather than over the whole base.
  4. Fuse signals and send only the top percentiles to manual or ML review.
  5. Act in waves, keep evidence, offer appeals, and never reveal the thresholds.

import statistics as st

def robust_z(x, population):
    med = st.median(population)
    mad = st.median([abs(v - med) for v in population]) or 1e-9
    return 0.6745 * (x - med) / mad

def suspicious(player, population):
    signals = {
        "headshot_rate": robust_z(player["hs"], population["hs"]),

Deterministic lockstep simulation

Deterministic lockstep simulation

An RTS does not transmit the world state, it transmits player commands: every client simulates the same thing and reaches the same result. That demands strict determinism — integer maths and a fixed update order.

fixed-pointdeterminismlockstep
01 Essence

Lockstep: every tick clients send their commands, wait for everyone's commands, and only then compute the next tick. Traffic is minimal (a few kilobytes per match) and a replay is just a command log. The price is that latency equals the slowest player, and any divergence (desync) breaks the match.

Determinism requires: a fixed step (say 20 ticks per second), integer or fixed-point arithmetic (Q16.16), a stable iteration order for containers, the same RNG implementation everywhere (xorshift with a saved state), no dependence on wall-clock time, and no reliance on hash-table ordering. Float arithmetic can produce different bits on different CPUs and compilers — the classic source of desync bugs.

Verification: each client hashes its state (CRC/FNV) every N ticks and compares. On a mismatch, save the state and the replay for analysis. To go faster, shard the simulation and parallelise with a fixed merge order; to smooth it visually, interpolate between ticks and predict your own units.

the mathematical model
xQ16.16 = round(x·216), a·b → (a·b) >> 16, hash = FNV-1a(state)
Tick: 20–30 Hz. Commands are applied at tick T + delay, identically for everyone.
02 How to build it
  1. Fix the tick rate and forbid any dependence of the simulation on real time.
  2. Move the game maths to fixed point or integers; check trigonometry and sqrt separately.
  3. Make the RNG part of the world state and include it in the hash.
  4. Sort every traversal (entities, collisions, timers) by a stable key.
  5. Compare hashes between clients and keep replays for desync debugging.

Snapshot compression and delta encoding

Snapshot compression and delta encoding

The network is expensive, so you transmit changes rather than “the whole world”: deltas, quantised values and bit masks. Information theory sets the lower bound and tells you where it is safe to lose precision.

Shannon entropyquantisationdelta
01 Essence

Shannon entropy H(X) = −Σ p(x)·log₂ p(x) is the average number of bits per symbol under optimal coding. If a unit position has 1024 possible values it needs 10 bits, not 32. Quantising position to 1 cm and rotation to 1° saves three to four times the bandwidth with no visible loss.

Delta encoding: send only the fields that changed since the confirmed snapshot, plus a bit mask of the changes. The baseline is the last confirmed snapshot, not the last one you sent — otherwise a lost packet breaks the whole chain. On top of that: change of basis (positions relative to a reference), areas of interest (close objects update more often and more precisely) and packet compression (zstd/lz4).

Budgets: aim for 10–30 KB/s per player in a shooter and 2–5 KB/s in an RTS. Measure not only the average bitrate but the tail (99th percentile) — the tail is what causes lag. Evaluate every field by “bits × change frequency”; in practice 80 % of the traffic is positions and rotations.

the mathematical model
H = −Σ pᵢ·log₂ pᵢ, bits ≈ log₂(range/step)
A position in 0–1024 m with a 0.01 m step needs 17 bits instead of 32. A quaternion: three components at 10–12 bits (smallest-three).
02 How to build it
  1. Inventory the state fields and how often each changes.
  2. Quantise with a tolerance the player cannot notice (scale the scene and the speed).
  3. Build deltas against the confirmed baseline and send a change bit mask.
  4. Prioritise objects by visibility and distance (AOI) and update them at different rates.
  5. Measure the 99th percentile of snapshot size and loss, not just the average.

import math

def quantize(value, min_v, max_v, bits):
    levels = (1 << bits) - 1
    t = (value - min_v) / (max_v - min_v)
    q = max(0, min(levels, int(round(t * levels))))
    return q

def dequantize(q, min_v, max_v, bits):
    levels = (1 << bits) - 1
    return min_v + (q / levels) * (max_v - min_v)

def delta(baseline, current, mask_fields):
    bits = 0
    changed = []
    for name, mask in mask_fields.items():
        if baseline.get(name) != current.get(name):
            bits += mask
            changed.append(name)
    return changed, bits

def entropy(counts, total):
    return -sum((c/total) * math.log2(c/total) for c in counts if c)

Procedural planetary systems

Procedural planetary systems

A planetary system is a hierarchy of orbits where the star's mass sets the scale of time and the orbital radius sets the climate. For gameplay, Keplerian orbits and sensible placement rules beat a full n-body simulation.

Kepler's lawsn-bodyhabitable zone
01 Essence

Kepler's third law: T² = 4π²a³/(G(M+m)). It ties the period to the semi-major axis, so a system is easy to generate in “astronomical units and years”: for a solar-mass star T(years) = a(AU)1.5. Kepler's equation M = E − e·sin E is solved with Newton's method to get the true anomaly and the position on the ellipse.

Plausibility rules: orbits are nearly coplanar (±5°), periods form resonances (2:1, 3:2), gas giants sit further out, rocky planets closer in, and the habitable zone lies where the flux is roughly Earth's. A full n-body simulation is overkill for gameplay and inherently chaotic; use it for spectacle, not for stable orbits.

Climate: stellar flux F = L/(4πa²), equilibrium temperature T ≈ 278·(L/L☉)1/4/√(a/AU) K. Then albedo, greenhouse effect, tides and axial tilt. For the visuals, draw orbits on a logarithmic scale so distant planets stay on screen while the labels keep the real periods.

the mathematical model
T² = 4π²a³ / (G(M+m)), M = E − e·sin E, F = L/(4πa²)
T in seconds, a in metres, M in kg. In game units: T(years) ≈ √(a(AU)³/M(M☉)).
02 How to build it
  1. Define the star: mass, luminosity, spectral class, age.
  2. Place planets with a log-uniform distribution of semi-major axes, forbidding overlaps.
  3. Add eccentricities and inclinations, then check stability over 10⁴ orbits.
  4. Compute flux and temperature, assign biome and atmosphere.
  5. Build the visualisation with scaling and labels; compute orbits analytically.

import math

def orbital_period_years(a_au, star_mass_solar=1.0):
    return math.sqrt(a_au ** 3 / star_mass_solar)   # Kepler's third law

def solve_kepler(M, e, tol=1e-10, iters=30):
    E = M
    for _ in range(iters):
        d = (E - e * math.sin(E) - M) / (1 - e * math.cos(E))
        E -= d
        if abs(d) < tol: break
    return E

def position(a, e, E):
    x = a * (math.cos(E) - e)
    y = a * math.sqrt(1 - e*e) * math.sin(E)
    return x, y

def equilibrium_temp(luminosity_solar, a_au, albedo=0.3):
    flux = luminosity_solar / (a_au ** 2)
    return 278.5 * flux ** 0.25 * (1 - albedo) ** 0.25

Balanced strategy map generation

Balanced strategy map generation

Map balance is not “identical starting zones” but equality of opportunity: connectivity, distance to resources, number of entrances and defensive value. You verify that with graphs and metrics.

graph theorysymmetryfairness
01 Essence

First generate the geometry (noise, regions, rivers), then build a connectivity graph of passable zones: nodes are areas, edges are passages, weights are path cost. Then evaluate the map with metrics: graph diameter, distance from each start to the resources, the number of chokepoints (articulation points), the share of passable area, and symmetry about axes or under rotation.

Symmetry comes in mirror (point symmetry — a 180° rotation, as in most RTS maps), axial and rotational flavours. It guarantees equal distances and timings, but makes maps predictable. Asymmetric maps are more interesting, yet they need compensation: different resources, different defence, different expansion speed — and a check that no side has a first-move advantage.

Validation: run thousands of bot matches on generated maps, look at win rates per race and per slot, time to first contact, and access to critical resources. A map where one start has three entrances and the other has one is broken, however pretty it looks. Often the cheapest path is to generate half and mirror it rather than balancing asymmetry heuristically.

the mathematical model
fairness = Σ wᵢ·|metric(startᵢ) − mean(metrics)|, between starts → 0
Metrics: distance to the nearest resources, to the centre, number of passages, share of “your” territory, time to key points.
02 How to build it
  1. Generate terrain and resources from a seed and mark the passable regions.
  2. Build the connectivity graph and check that all starts sit in one component.
  3. Place starts symmetrically, or with compensation derived from the metrics.
  4. Compute the fairness metrics and reject maps with outliers.
  5. Run bots and watch the win-rate telemetry; when it is off, fix the rules rather than individual maps.

from collections import deque

def bfs_dist(graph, start):
    dist, q = {start: 0}, deque([start])
    while q:
        u = q.popleft()
        for v, w in graph[u]:
            if v not in dist:
                dist[v] = dist[u] + w
                q.append(v)
    return dist

def fairness(graph, starts, resources):
    scores = {}
    for s in starts:
        d = bfs_dist(graph, s)
        reachable = [d[r] for r in resources if r in d]
        scores[s] = sum(sorted(reachable)[:3]) / 3   # the 3 nearest resources
    mean = sum(scores.values()) / len(scores)
    spread = max(abs(v - mean) for v in scores.values())
    return mean, spread          # spread measures the imbalance

Lotka–Volterra ecosystems

Lotka–Volterra ecosystems

An ecosystem is a system of differential equations for “predator vs prey” plus the rules of a trophic web. Simple equations give cycles, but for a game stability matters more than mathematical beauty.

Lotka–Volterradynamical systemstrophic webs
01 Essence

The basic model: dx/dt = αx − βxy (prey), dy/dt = δxy − γy (predator). The solution is closed cycles around the equilibrium: populations oscillate without damping. In a game that looks like waves of population, but in practice numbers fall to zero because of discreteness and randomness. So add environmental capacity (logistic growth) and noise.

Logistics: dx/dt = αx(1 − x/K) − βxy. With capacity K the system gains a stable focus or a limit cycle. With three or more species, chaos and extinctions become possible; to keep the ecosystem alive use “immigration” (spawning from a pool), refuges (prey hide), seasonality and upper/lower bounds on predators.

For gameplay a discrete per-tick model is more practical: x′ = clamp(x + (births − deaths − predation)·dt) with whole individuals. Simulate populations, not every wolf; individual behaviour belongs in a separate system (boids/FSM). The player must see the causal chain: kill the deer and the wolves come to the village — otherwise the simulation is unreadable.

the mathematical model
dx/dt = αx(1 − x/K) − βxy, dy/dt = δxy − γy
α — prey birth rate, β — predator efficiency, δ — biomass conversion, γ — predator death rate, K — carrying capacity.
02 How to build it
  1. Define the species and the trophic links; start with 3–5 species, no more.
  2. Choose parameters so the equilibrium is stable for reasonable initial conditions.
  3. Add stochasticity, seasonality and immigration to avoid extinction to zero.
  4. Discretise per tick and clamp the values; watch the populations over long runs.
  5. Show the populations in the UI — otherwise the player cannot tell that the ecosystem works at all.

def ecosystem_tick(prey, pred, alpha=1.1, beta=0.4,
                   delta=0.1, gamma=0.9, K=100.0, dt=0.1):

    d_pred = delta * prey * pred - gamma * pred
    prey = max(0.0, prey + d_prey * dt)
    pred = max(0.0, pred + d_pred * dt)
    return prey, pred

Procedural music with L-systems

Music is generated on two levels: structure (forms, sections) with grammars and L-systems, and notes with Markov chains over scale and harmony. The constraints of music theory make randomness meaningful.

L-systemsmusic theoryMarkov chains
01 Essence

An L-system is a parallel rewriting grammar: an axiom is expanded by rules N times, then the symbols are interpreted as musical events. For example F → F+G, G → F−G produces self-similar rhythmic figures. Unlike plain randomness, L-systems produce structure with repetition and variation — which is what the brain hears as music.

Harmony: choose chords from a scale by functional logic (tonic–subdominant–dominant) or with a Markov chain trained on a corpus. The melody is a random walk over chord tones with a pull towards stable scale degrees; strong beats carry chord tones, weak beats passing tones. Rhythm comes from trees or Euclidean rhythms (E(5,8) gives the “cubian” pattern).

For adaptive music (vertical remixing) tracks are split into layers: bass, harmony, melody, percussion. Layer gain follows gameplay intensity, and tempo and key stay synchronised. Seamlessness matters: switch on bar boundaries, not at random moments, and use “stinger” phrases for events.

the mathematical model
A → B, B → A+B (L-system), P(notei | notei−1, chord)
Euclidean rhythm E(k, n): k beats spread as evenly as possible over n steps — a hit when floor(i·k/n) changes.
02 How to build it
  1. Define the scale, tempo, time signature and the set of layers.
  2. Generate a rhythmic pattern (Euclidean rhythm or an L-system).
  3. Generate the chord progression with functional logic or a Markov chain.
  4. Build the melody on chord tones with limits on intervals and range.
  5. Tie layer intensity to gameplay and switch sections on bar boundaries.

import random

SCALE = [0, 2, 4, 5, 7, 9, 11]        # ionian scale
CHORDS = {"I": [0, 4, 7], "IV": [5, 9, 12], "V": [7, 11, 14], "vi": [9, 12, 16]}

def lsystem(axiom, rules, iterations):
    s = axiom
    for _ in range(iterations):
        s = "".join(rules.get(c, c) for c in s)
    return s

def euclid(k, n):
    return [1 if ((i * k) % n) < k else 0 for i in range(n)]

def melody(progression, steps=16, rng=random):
    notes, degree = [], 0
    for bar, chord in enumerate(progression):
        for i in range(steps):
            if rng.random() < 0.7:
                degree = max(-3, min(9, degree + rng.choice([-2, -1, 0, 1, 2])))
            octave, idx = divmod(degree, len(SCALE))
            tone = 12 * octave + SCALE[idx]
            if i % 4 == 0:                # strong beat: a chord tone
                tone = 12 * (degree // 7) + CHORDS[chord][i // 4 % 3]
            notes.append(tone)
    return notes

Cloth and soft bodies (Verlet, XPBD)

Cloth and soft bodies (Verlet, XPBD)

Cloth is a grid of particles linked by length constraints. Verlet gives free damping and a simple implementation, while XPBD adds stability under stiff constraints.

mass-springVerlet integrationXPBD
01 Essence

Verlet without an explicit velocity: x′ = 2x − xprev + a·dt². The position is updated from the two previous ones and the velocity is implicit — that makes the scheme stable and lets you apply constraints directly to positions. The constraint “the distance between two particles equals L” is solved by projection: move both points along the connecting line by a fraction of the error. 10–20 iterations give cloth that is stiff but does not explode.

A mass-spring model with stiff springs needs a tiny dt or implicit integration. Cloth and ropes therefore use the constraint-based approach (PBD/XPBD), where stiffness is expressed through compliance α instead of a huge coefficient k. XPBD: Δλ = (−C − α̃λ)/(w₁ + w₂ + α̃), where C is the constraint error — this makes stiffness independent of the iteration count.

For gameplay what matters is collision with the character capsule, wind as a force per area, tearing past a deformation threshold, LOD, and “freezing” cloth that is off screen. Cloth with hundreds of particles is expensive; capes usually use skinning plus bones with physics instead of a full mesh.

the mathematical model
Verlet: x′ = 2x − xprev + a·dt², PBD: Δx = ±w/(w₁+w₂)·C, XPBD: α̃ = α/dt²
C — the constraint function (for example |x₁−x₂| − L). w — inverse mass. α = 0 means a hard constraint.
02 How to build it
  1. Build the grid of particles and constraints (structural, shear, bend).
  2. Set the pinned points and the initial positions; keep the previous positions.
  3. Each sub-step: integrate with Verlet, then run N iterations of constraint projection.
  4. Handle collisions (spheres, capsules, planes) after or inside the projections.
  5. Add wind, damping, tearing and LOD; put invisible cloth to sleep.

import math

def verlet(x, x_prev, acc, dt):
    # x' = 2x - x_prev + a*dt^2; velocity is implicit
    nx = [2 * x[i] - x_prev[i] + acc[i] * dt * dt for i in range(len(x))]
    return nx, list(x)

def solve_distance(p1, p2, rest, w1, w2, stiffness=1.0):
    # C = |p1-p2| - rest; move both points along the line by the error
    dx, dy = p2[0] - p1[0], p2[1] - p1[1]
    d = math.hypot(dx, dy)
    if d < 1e-9:
        return p1, p2
    C = d - rest
    wsum = w1 + w2
    if wsum <= 0:
        return p1, p2
    k = stiffness * C / wsum
    return ([p1[0] + dx / d * k * w1, p1[1] + dy / d * k * w1],
            [p2[0] - dx / d * k * w2, p2[1] - dy / d * k * w2])

Aerodynamics and flight models

Aerodynamics and flight models

Lift scales with density, the square of speed and wing area, and the lift coefficient depends on the angle of attack. That formula is enough for arcade flight; a simulator needs tables and stall behaviour.

BernoulliCFDaerodynamic coefficients
01 Essence

Lift: L = ½·ρ·v²·S·CL(α), drag: D = ½·ρ·v²·S·CD(α). CL grows linearly with the angle of attack up to a critical value (~15°), then collapses — that is the stall, which makes the aircraft drop. CD = CD0 + CL²/(π·e·AR): induced drag grows with lift.

Bernoulli's principle explains part of the picture (faster flow, lower pressure), but lift is described better by flow deflection and circulation (Zhukovsky's theorem: L = ρ·v·Γ). For a game the empirical curves CL(α) and CD(α) matter more than physical accuracy. CFD is used for design and pre-computation; at runtime it is replaced by tables.

The flight model: forces in a body frame (thrust, lift, drag, weight), moments from ailerons, rudder and elevator, plus inertia. Damping moments provide stability. Arcade games simplify: the aircraft levels itself, roll steers the turn, and stall is disabled. A simulator wants honest aerodynamics, trimming, and air density that falls with altitude.

the mathematical model
L = ½ρv²S·CL(α), D = ½ρv²S·(CD0 + CL²/(πeAR))
ρ falls with altitude: ρ ≈ ρ₀·(1 − 2.2557e−5·h)4.2559. Stall at α > αcrit ≈ 15°.
02 How to build it
  1. Set mass, wing area, span and the CL/CD curves versus angle of attack.
  2. Compute body-frame velocities, the angle of attack and the sideslip.
  3. Compute forces and moments, then apply angular damping.
  4. Add thrust, weight, air density versus altitude and stall behaviour.
  5. Tune the controls: assists for arcade, trim and honest axes for a simulator.

import math

def cl_cd(alpha_deg, cl_alpha=0.09, cl_max=15.0, cd0=0.025, k_induced=0.05):
    a = math.radians(alpha_deg)
    if abs(a) <= math.radians(cl_max):
        cl = cl_alpha * a
    else:
        # past the critical angle the lift collapses (stall)
        over = (abs(a) - math.radians(cl_max)) / math.radians(5)
        cl = math.copysign(cl_alpha * math.radians(cl_max) * max(0.0, 1.0 - over), a)
    cd = cd0 + k_induced * cl * cl
    return cl, cd

def forces(mass, speed, area, rho, alpha_deg, cl=None, cd=None):
    cl_c, cd_c = (cl, cd) if cl is not None else cl_cd(alpha_deg)
    q = 0.5 * rho * speed * speed * area
    return q * cl_c, q * cd_c

Vector fields, divergence and curl

Vector fields, divergence and curl

A field defines a force at every point in space. Divergence shows sources, curl shows vortices; together they tell you whether a field can be expressed as a potential and how to visualise it without chaos.

vector fieldsdivergence/curlpotential
01 Essence

A vector field F(x, y) = (P, Q). The divergence ∇·F = ∂P/∂x + ∂Q/∂y is the density of sources; the curl (a scalar in 2D) ∇×F = ∂Q/∂x − ∂P/∂y is local rotation. A magnetic field in vacuum is source-free (∇·B = 0), an electrostatic field is potential (∇×E = 0). Gravity is a potential field too, with ∇·g = −4πGρ.

In games, fields are usually built by summing sources: a point charge or mass gives F = k·q·r̂/r², a dipole a more complex pattern. The sum needs softening: as r → 0 the force must not diverge, or objects get flung. For planets use a spherically symmetric model (linear growth inside) rather than a point singularity.

Visualisation: streamline curves integrate dx/ds = F(x)/|F(x)|, colour follows the magnitude, arrows the direction. For gameplay, readability wins: do not draw the field where it does not matter, limit the number of lines and use animated dashes. For magnetic puzzles, equipotential lines are useful — they hint where an object will roll.

the mathematical model
F = k·q·r̂/r², ∇·F = ∂P/∂x + ∂Q/∂y, ∇×F = ∂Q/∂x − ∂P/∂y
Softening: F = k·q·r̂/(r² + ε²). Potential φ: F = −∇φ; for a point mass φ = −GM/r.
02 How to build it
  1. Define the field sources and the force law (1/r², dipole, vortex).
  2. Add softening and a maximum force for stability.
  3. Evaluate forces for dynamic objects; for static ones, pre-bake the field into a texture.
  4. Visualise streamlines or equipotentials with a bounded density.
  5. Check the integrator's stability: a field with strong gradients needs sub-steps.

import math

def field_force(sources, x, y, softening=0.5, max_force=1e4):
    fx = fy = 0.0
    for sx, sy, strength in sources:
        dx, dy = x - sx, y - sy
        r2 = dx * dx + dy * dy + softening * softening
        inv = strength / (r2 * math.sqrt(r2))     # k*q*r_hat / (r^2 + eps^2)
        fx += dx * inv
        fy += dy * inv
    mag = math.hypot(fx, fy)
    if mag > max_force:                          # clamp for stability
        fx = fx / mag * max_force
        fy = fy / mag * max_force
    return fx, fy

Heat diffusion and thermodynamics

Heat diffusion and thermodynamics

Heat flows from hot to cold in proportion to the temperature gradient. The heat equation is a diffusion; in games it is solved on a grid or simplified into “zones” with a heat capacity.

Fourier's equationdiffusionentropy
01 Essence

Fourier's equation: ∂T/∂t = α·∇²T, where α = k/(ρcp) is the thermal diffusivity. On a grid this is an explicit scheme: T′ᵢ = Tᵢ + α·dt/h²·(Tᵢ₋₁ − 2Tᵢ + Tᵢ₊₁). The stability condition is α·dt/h² ≤ 0.25 in 2D (≤ 1/6 in 3D). Breaking it produces oscillations and a checkerboard — the classic mistake.

For gameplay a “zone” model is often enough: rooms with a temperature, a heat capacity and connections (doors, ventilation). Then heat exchange is Q = k·(T₁ − T₂) and T′ᵢ = Tᵢ + Q/cᵢ. It is stable, cheap and readable: the player sees that an open door cools the room. For visuals, add a heat map and steam or ice as indicators.

Thermodynamics: the first law ΔU = Q − W (energy is conserved), the second — entropy does not decrease in a closed system. In games the second law is a design constraint: no perpetual motion without heat rejection. Cooling, efficiency and overheating equipment become natural mechanics for sci-fi and survival, as long as the numbers are shown to the player.

the mathematical model
∂T/∂t = α∇²T, explicit: T′ᵢ = Tᵢ + α·dt/h²·(Tᵢ₋₁ − 2Tᵢ + Tᵢ₊₁)
Stability: α·dt/h² ≤ 1/4 (2D), ≤ 1/6 (3D). Otherwise use an implicit scheme (Crank–Nicolson).
02 How to build it
  1. Choose the representation: a grid for visuals, zones for gameplay.
  2. Set the heat sources, heat capacities and the conductivity of the materials.
  3. Check the stability condition or switch to an implicit scheme.
  4. Connect the temperature to effects: damage, freezing, steam, overheating.
  5. Show numbers and colours — the player must understand why they are freezing.

import math

def heat_step(T, alpha, dt, h=1.0):
    # explicit diffusion; stability needs alpha*dt/h^2 <= 0.25 in 2D
    if alpha * dt / (h * h) > 0.25:
        raise ValueError("unstable step: use sub-steps or an implicit scheme")
    n = len(T)
    out = [0.0] * n
    for i in range(n):
        left  = T[i - 1] if i > 0 else T[i]
        right = T[i + 1] if i < n - 1 else T[i]
        out[i] = T[i] + alpha * dt / (h * h) * (left - 2 * T[i] + right)
    return out

def zone_exchange(zones, edges, dt=1.0):
    # zones: {id: (temperature, capacity)}; edges: [(a, b, k)]
    temps = {k: v[0] for k, v in zones.items()}
    caps  = {k: v[1] for k, v in zones.items()}
    for a, b, k in edges:
        q = k * (temps[a] - temps[b]) * dt
        temps[a] -= q / caps[a]
        temps[b] += q / caps[b]
    return temps

  • Entropy as a “magical” resource without rules confuses players; tie it to a concrete mechanic.

Frame scheduling and work distribution

Frame scheduling and work distribution

The frame budget is a scheduling problem: you have 16.6 ms and a set of jobs with different costs and dependencies. Formally it is LP/ILP; practically it is priorities, task pools and cutting work at the budget.

linear programmingsimplexjob system
01 Essence

The formalisation: maximise Σ uᵢ·xᵢ subject to Σ cᵢ·xᵢ ≤ B (the budget), dependencies (xᵢ ≤ xⱼ) and integrality. The simplex method solves the continuous relaxation and rounding gives a nearly optimal schedule. In practice jobs (shadows, GI, particles, physics) are discrete with hard dependencies, so a greedy algorithm on “utility per millisecond” with cutoff is the usual answer.

Job system: a pool of tasks with dependencies (a DAG), worker threads, lock-free queues. The key is to minimise synchronisation and to size the tasks well: tasks that are too small drown in overhead, tasks that are too large give no balance. For the GPU, use command buffers and asynchronous compute queues so you never wait for a copy.

Adaptive quality: measure the actual time of each system, keep a moving average, and decide what to lower when the budget is exceeded. The policy needs hysteresis so quality does not flicker every frame. And keep separate CPU and GPU budgets: they overlap, but synchronisation can eat the gain.

the mathematical model
max Σ uᵢxᵢ s.t. Σ cᵢxᵢ ≤ B, xᵢ ∈ {0,1}
Greedy approximation: sort by uᵢ/cᵢ and add while the budget lasts. The LP relaxation gives an upper bound on the optimum.
02 How to build it
  1. Split the frame into systems and measure their cost (P50/P95).
  2. Build a dependency DAG and parallelise the independent branches.
  3. Set priorities and a cutoff policy for when the budget is exceeded.
  4. Implement a task pool with worker threads and minimal synchronisation.
  5. Add adaptive quality with hysteresis and log the decisions.

def greedy_schedule(tasks, budget_ms):
    """tasks: [(name, cost_ms, utility, [dependencies])]"""
    done, used, plan = set(), 0.0, []
    remaining = list(tasks)
    while remaining:
        ready = [t for t in remaining if all(d in done for d in t[3])]
        if not ready:
            break
        # highest utility per millisecond first
        best = max(ready, key=lambda t: t[2] / max(t[1], 1e-6))
        if used + best[1] > budget_ms:
            break                       # out of budget: cut the rest
        plan.append(best[0])
        used += best[1]
        done.add(best[0])
        remaining.remove(best)
    return plan, used

  • Adaptive quality without hysteresis flickers and annoys more than a dip would.
  • A CPU→GPU synchronisation in the middle of the frame kills the parallelism — put it at the end.

Spatial partitioning (BVH, k-d tree, grid)

Spatial partitioning (BVH, k-d tree, grid)

Testing every pair is O(n²). A spatial index discards obviously distant pairs and turns collisions into an almost linear problem.

BVHk-d treebroadphase
01 Essence

Broadphase: build an AABB per object, let the index find the intersecting pairs, then run the narrowphase on the exact geometry (GJK, SAT, triangles). Index options: a uniform grid (fast, but poor when object scales differ), sweep-and-prune (sort along an axis, good for nearly sorted data), a BVH (an AABB hierarchy — the best choice for static geometry and raycasts) and a k-d tree (good for point queries and nearest-neighbour searches).

A BVH is built top-down: pick an axis (SAH — the surface area heuristic), sort by centroids, split in half. SAH minimises the expected traversal cost: cost = Ctrav + (SL/S)·CL + (SR/S)·CR. For dynamic objects you refit parts of the tree or keep several trees by layer.

Important: broadphase does not replace the exact test, it only reduces the number of pairs. For thousands of projectiles a fixed-cell grid with pair de-duplication wins. For mesh raycasts, a BVH with ordered traversal (nearest child first) and early exit is the answer. Cache locality decides the rest: a flat array of structs beats a tree of pointers.

the mathematical model
SAH: cost = Ctrav + (SL/S)·CL + (SR/S)·CR
S — the AABB surface area. For a grid: cell size ≈ the average object size; with varied sizes use a hierarchical grid.
02 How to build it
  1. Collect the AABBs and pick a structure for the scenario (grid, BVH, SAP).
  2. Build the index; once for static geometry, refit or rebuild for dynamic content.
  3. Query the pairs and pass them to the narrowphase with layer filters.
  4. For raycasts, traverse with a nearest-node priority and an early exit.
  5. Profile build, queries and updates separately — they are three different budget lines.

import math

def union(boxes):
    return (min(b[0] for b in boxes), min(b[1] for b in boxes),
            max(b[2] for b in boxes), max(b[3] for b in boxes))

def overlaps(a, b):
    return not (a[2] < b[0] or b[2] < a[0] or a[3] < b[1] or b[3] < a[1])

class Node:
    __slots__ = ("box", "left", "right", "items")
    def __init__(self, box):
        self.box = box          # (minx, miny, maxx, maxy)
        self.left = self.right = None
        self.items = []

def build(boxes, depth=0):
    node = Node(union(boxes))
    if len(boxes) <= 4 or depth > 24:
        node.items = boxes
        return node
    # split along the longest axis at the median centroid
    ex = node.box[2] - node.box[0]
    ey = node.box[3] - node.box[1]
    axis = 0 if ex >= ey else 1
    boxes = sorted(boxes, key=lambda b: (b[axis] + b[axis + 2]) * 0.5)
    mid = len(boxes) // 2
    node.left = build(boxes[:mid], depth + 1)
    node.right = build(boxes[mid:], depth + 1)
    return node

Animation compression (quantization + curve fitting)

Animation compression (quantization + curve fitting)

Animation is rotation and position curves sampled at a high rate. You compress them by quantising, dropping keys within a tolerance and fitting splines; the crucial part is not to lose footfalls and sharp impacts.

quantisationsplinescurves
01 Essence

A quaternion takes 16 bytes; it is quantised to 4×16 bits (8 bytes) or to 3×10 bits plus a sign (smallest-three). At a tolerance of 0.1° this is visually invisible. Positions and scales are quantised over the skeleton's range; small bones (fingers) need a smaller range, so they can spend fewer bits.

The key step is key removal: the curve is approximated within a tolerance (say 0.5 cm / 0.5°), redundant keys are dropped and the rest are encoded as Hermite splines with tangents. The algorithm is greedy: extend the segment while the error stays below the tolerance. That gives a 5–20× compression on smooth clips and less on sharp ones.

Advanced techniques: significance-based curve simplification, delta encoding against the A-pose, a different sample rate per bone, and separate compression for translation and rotation. For large clips, split into chunks and stream them. Validate by comparing the visual result and the maximum deviation — not the average; the eye notices the peaks.

the mathematical model
bits ≈ log₂(range/tolerance), 3-component quaternion: 32 bits → 30 bits + sign
Approximation error: max|curve(t) − approx(t)| < tolerance over the whole interval.
02 How to build it
  1. Define rotation and position tolerances per bone, based on its size and visibility.
  2. Convert quaternions to a compact representation (smallest-three).
  3. Simplify the curves greedily while tracking the maximum error.
  4. Encode the remaining keys as splines with tangents and compress the stream.
  5. Check visually and by peak error; use tighter tolerances for sharp clips.

def simplify(keys, tolerance, metric=lambda a, b: abs(a - b)):
    """Greedy key removal: keep points while the linear interpolation
    error stays below the tolerance."""
    if len(keys) < 3:
        return list(keys)
    out = [keys[0]]
    last = 0
    for i in range(2, len(keys)):
        # check every intermediate point against the segment last -> i
        ok = True
        for j in range(last + 1, i):
            t = (keys[j][0] - keys[last][0]) / (keys[i][0] - keys[last][0])
            approx = keys[last][1] + t * (keys[i][1] - keys[last][1])
            if metric(keys[j][1], approx) > tolerance:
                ok = False
                break
        if not ok:
            out.append(keys[i - 1])
            last = i - 1

Profiling and the frame budget

Profiling and the frame budget

Optimising without measuring is guessing. First fix the frame budget (16.6 ms at 60 Hz), then find out where it goes, and only then change code. Profile the tail, not the average: p95 and p99 show what players experience as stutter.

profilerframe budgetp95throttling
01 Essence

The frame budget is a hard sum: 16.67 ms at 60 Hz, 8.33 ms at 120 Hz, 33.3 ms at 30 Hz. Inside the budget you divide time between subsystems: gameplay, physics, AI, animation, rendering (CPU and GPU), audio, input, streaming. The rule is simple: a subsystem that keeps exceeding its quota is either optimised or given a smaller quota — otherwise “optimising” one part eats another part's headroom.

A profiler has to be cheap and always on: counters around subsystems, not just a flame graph in the editor. The key metric is not the average but percentiles: an average of 6 ms with a p99 of 40 ms means the game hitches ten times a second. Hitches — frames longer than 2× the budget — deserve their own hunt; they are almost always an allocation, a resource load, a shader compilation or a GPU synchronisation.

Production profiling differs from studio profiling: the player has different hardware, different drivers and different thermal throttling. So you need built-in telemetry: frame time percentiles, the hottest systems (aggregated by name), driver version, GPU type. Throttling shows up as the frame rate dropping 15–25 % after ten minutes of play — that is not an engine bug but heat, and it is fixed with quality, not with code.

the mathematical model
frame_time = sim + physics + ai + render_cpu + gpu + audio + io, budget = 1 / target_fps
Quotas are set up front (say sim 4 ms, render_cpu 3 ms, gpu 7 ms). A profile is a distribution, not a number: look at p50/p95/p99 and the share of frames that fit the budget.
02 How to build it
  1. Fix the target frame rate and convert it to milliseconds: 1/fps.
  2. Give each subsystem a quota and add counters that build a histogram, not just a “last frame” value.
  3. Find the three most expensive subsystems and the three main hitch sources (usually: allocation, streaming, shader compilation, readback).
  4. Track p50/p95/p99 and the share of frames inside the budget — those numbers show the real picture, not the average.
  5. Add telemetry: hardware, driver, clocks, temperature, build version — otherwise you are fixing someone else's problem.
  6. Verify on cold hardware (integrated GPU, 4K) and in long sessions where throttling kicks in.

import time, statistics, collections

class Profiler:
    """Minimal counter: accumulates a histogram of frame times."""
    def __init__(self):
        self.frames = collections.deque(maxlen=4096)
        self.sections = collections.defaultdict(lambda: collections.deque(maxlen=4096))

    def begin(self, name):
        return time.perf_counter()

    def end(self, name, t0):
        self.sections[name].append((time.perf_counter() - t0) * 1000.0)

    def frame(self, ms):
        self.frames.append(ms)

    def report(self):
        fr = sorted(self.frames)
        if not fr:
            return {}
        def pct(p):
            return fr[min(len(fr) - 1, int(len(fr) * p))]
        out = {
            "p50": round(pct(0.50), 2),
            "p95": round(pct(0.95), 2),
            "p99": round(pct(0.99), 2),
            "hitch%": round(100.0 * sum(1 for f in fr if f > 33.3) / len(fr), 2),
        }
        for name, vals in self.sections.items():
            out[name] = round(statistics.mean(vals), 2)
        return out

Batching, instancing and draw-call reduction

Batching, instancing and draw-call reduction

A modern GPU does not die from triangles, it dies from draw calls: every call is a trip into the driver, a pipeline state change and a synchronisation. 1000 calls of 100 triangles hurt far more than 100 calls of 100 000 triangles.

draw callinstancingSRP Batcherindirect draw
01 Essence

Each draw call switches pipeline state: shader, buffers, textures, blend, depth state. When the state changes, the GPU flushes internal caches (pipeline stalls) and the real cost of the call jumps from 1–2 µs to hundreds. Hence the rule: sort objects by material and by shader so that the number of switches is minimal — not “sort by Z for transparency” at any cost.

Instancing draws N copies of one mesh in a single call: the poses come from a buffer and the variations (colour, wind, UV offset) from instance attributes. It scales linearly: 10 000 trees are one call instead of ten thousand. The limitation is that every copy shares one material. Different textures are solved with atlases, different shaders with texture arrays or bindless rendering.

The next step is the modern approach: a GPU-driven pipeline where sorting, culling and command assembly happen on the GPU and the CPU issues a single command with an indirect buffer (see topic 60). A pragmatic middle ground is to sort on the CPU by key (shader, material, world chunk), merge neighbours and submit in batches. It also helps to separate “cost of the call” from “cost of the state change”: 500 calls with one material are cheaper than 50 calls that switch the shader every time.

the mathematical model
frame_cpu ≈ draw_calls · c_call + state_changes · c_state + Σ shader_switches
Typical magnitudes: c_call ≈ 1–5 µs (CPU), c_state ≈ 10–100 µs on a pipeline cache miss. The goal is hundreds of draw calls and tens of state changes.
02 How to build it
  1. Measure draw calls and state changes (RenderDoc and Pix give you the counters ready-made).
  2. Sort the scene by key (shader + material + world chunk) — on the CPU that is a cheap O(n log n) with cached keys.
  3. Merge objects that share a material into instances; pack textures into atlases or arrays.
  4. For thousands of identical objects, move to indirect draw and let the GPU pick what is visible.
  5. Watch the state changes: any shader or blend switch inside the loop is a sorting candidate.
  6. Do not batch what does not need drawing: cull first, batch second (topic 33).

Culling: frustum, occlusion and LOD

Culling: frustum, occlusion and LOD

Culling answers the question “what does not need drawing at all”. Frustum culling removes what is behind the camera, occlusion culling removes what is hidden behind other objects, LOD changes detail with distance. Together they typically cut 70–95 % of the rendering work.

frustum cullingocclusionLODHLODHZB
01 Essence

Frustum culling is the cheapest test: six planes from the camera matrix, an object's AABB against them. Test objects against bounding volumes rather than one by one: one large BVH node that is culled takes all of its children with it.

Occlusion culling answers the question frustum cannot: the object is in view but behind a wall. The classic approach is an occluder hierarchy — large potential “blockers” (walls, rooms) are picked, a depth buffer is rendered for them, and then a query asks whether this object is visible. It has to be asynchronous: the answer arrives one or two frames later, so the decision uses last frame's data, and a suddenly opened door gets an occlusion fade over 100–200 ms.

LOD changes quality with distance without losing the silhouette, only simplifying the small stuff. The key is not “distance to the camera” but the on-screen size (pixel size): thresholds must differ per resolution and FOV. Transitions need cross-fades or dithering, otherwise you get popping. For huge worlds use HLOD — one merged model per group of objects — plus sector streaming.

the mathematical model
visible = frustum_culled · occlusion_culled · lod_selected; screen_size ≈ (2·r·f) / (d · tan(fov/2))
d — distance, r — object radius, f — focal length in pixels. Set the LOD threshold by screen size (e.g. 64 px for the highest level).
02 How to build it
  1. Compute the on-screen size of an object and pick the LOD by it, not by distance.
  2. Group objects into a hierarchy: a culled node culls all of its descendants.
  3. For occlusion culling, pick an occluder hierarchy and render only depth for it, at low resolution.
  4. Use the occlusion result with a delay of one to two frames and add a fade for sudden reveals.
  5. Enable temporal coherence: do not recompute culling for objects that have not moved and did not move the camera.
  6. Track not only draw calls in the HUD but also “culled %” — that is the main metric of a culling system.

import math

def extract_frustum_planes(view_proj):
    """Six planes (nx, ny, nz, d) from a view-projection matrix (column-major).
    A plane: normal.p + d = 0; a point is inside when it is > 0."""
    m = view_proj
    rows = [
        [m[3] + m[0], m[7] + m[4], m[11] + m[8],  m[15] + m[12]],   # left
        [m[3] - m[0], m[7] - m[4], m[11] - m[8],  m[15] - m[12]],   # right
        [m[3] + m[1], m[7] + m[5], m[11] + m[9],  m[15] + m[13]],   # bottom
        [m[3] - m[1], m[7] - m[5], m[11] - m[9],  m[15] - m[13]],   # top
        [m[3] + m[2], m[7] + m[6], m[11] + m[10], m[15] + m[14]],   # near
        [m[3] - m[2], m[7] - m[6], m[11] - m[10], m[15] - m[14]],   # far
    ]
    planes = []
    for r in rows:
        nx, ny, nz, d = r
        inv = 1.0 / math.sqrt(nx * nx + ny * ny + nz * nz)
        planes.append((nx * inv, ny * inv, nz * inv, d * inv))
    return planes

def aabb_in_frustum(planes, center, half):
    """AABB (center, half-extents) against a list of planes."""
    for nx, ny, nz, d in planes:
        # distance from the centre to the plane minus the projected half-extent
        dist = nx * center[0] + ny * center[1] + nz * center[2] + d
        radius = half[0] * abs(nx) + half[1] * abs(ny) + half[2] * abs(nz)
        if dist < -radius:
            return False   # the AABB is entirely behind the plane
    return True

Data-oriented design, SIMD and cache friendliness

Data-oriented design, SIMD and cache friendliness

Most game loops are not limited by arithmetic but by memory: the processor waits for data from DRAM. Data-oriented design lays data out so traversals run linearly through memory, and SIMD processes 4–16 values per instruction.

SoASIMDcachealignmentAoS
01 Essence

AoS (an array of structs) is convenient for humans: `struct Transform { vec3 pos; quat rot; }`. But a loop that “updates all transforms” reads 28 bytes per object and uses maybe 12 of them, wasting cache lines (64 bytes). SoA (a struct of arrays) splits the data by field: all positions here, all angles there. Now the loop reads a dense position array — 12 bytes per object — and SIMD instructions handle four floats at once.

The second layer is alignment and prefetching. A cache line is 64 bytes; a structure should occupy a whole number of lines (padding), and arrays should be aligned to 16/32 bytes for SIMD. False sharing — two threads writing to different fields of the same cache line — destroys multithreading: an “atomic” counter without padding can be ten times slower than a plain one.

The rule of the data layer: lay out first, write code second. Hot arrays (positions, velocities, HP) that are rewritten every frame are kept apart from cold ones (item descriptions, texts) that are touched rarely. Structural patterns (ECS, components, systems) are a way to express that layout in code, not an end in itself.

the mathematical model
memory_time ≈ (bytes_touched / bandwidth_peak) + (cache_misses · latency), SIMD_speedup ≤ min(n_lanes, memory_bound_ratio⁻¹)
Cache: L1 ~1–2 ns, L2 ~4–12 ns, DRAM ~80–120 ns. One cache miss costs as much as dozens of instructions — which is why the order of data matters more than the amount of arithmetic.
02 How to build it
  1. Write down the hot loops (physics, AI, animation) and count the bytes they read per frame.
  2. Convert the structures to SoA for the data that is rewritten every frame.
  3. Align arrays to 32 bytes and add padding where structures are written from different threads.
  4. Enable vectorisation: unroll the loop, avoid branches inside the iteration, use fma.
  5. Check whether the loop is memory-bound: if the arithmetic is nearly free but the time is large, memory is to blame.
  6. Measure on real hardware: desktop caches are generous, consoles and mobile are not.

            Position[w] = Position[i];
            Velocity[w] = Velocity[i];
            Life[w] = Life[i];
            w++;
        }
        Count = w;

Multithreading and the job system

Multithreading and the job system

One frame is hundreds of independent jobs: physics, AI, animation, particles, audio, streaming. A job system splits them into tasks and hands them to threads. The main rule: keep the main thread idle and the frame predictable.

job systemwork stealingtasksmain thread
01 Essence

The classic mistake is “parallelising the game loop”: the main thread still waits for the slowest thread, and shared data needs locks. The right shape is a job system: work is split into small tasks with explicit dependencies, a scheduler distributes them across workers, and results are read after a join. Dependencies are expressed as “reads from buffer X”, which is also what lets tasks migrate to the GPU.

Work stealing solves the imbalance: workers take tasks from a shared queue and, when it is empty, from their neighbours' queues. The scheduler hands out large tasks first (visibility sorting) and small ones later (updating individual particles) so no thread idles. Scheduling must be deterministic when the network needs it, or you explicitly accept non-determinism and synchronise only the result.

The main thread should only assemble the frame: read input, update the camera, issue render commands. Everything that can go to a worker goes. Latency matters too: a task that should take 0.1 ms but waited 5 ms in the queue hurts control feel far more than a frame-rate dip. Hence priorities: input and camera first, streaming and prediction last.

the mathematical model
T_frame ≈ max(T_main, T_work / P) + T_sync, efficiency = Σ T_task / (P · T_frame)
P — number of workers. Amdahl: with a sequential fraction s the speed-up is at most 1/(s + (1−s)/P). The scheduler aims for balance: std(duration of tasks) → 0.
02 How to build it
  1. Measure the share of the main thread: if it is above 30 %, that is the first optimisation target.
  2. Split gameplay into tasks: physics per chunk, AI per unit, animation per character.
  3. Describe dependencies explicitly (buffer → buffer) and let the scheduler reorder independent tasks.
  4. Enable work stealing and priorities: input and camera first, streaming last.
  5. Cap the number of workers: two to four on mobile, closer to the core count on consoles, without hyper-threading.
  6. Measure always in a release build with debug code off: asserts and logging eat threads.
03 Working code

using System.Collections.Concurrent;
using System.Threading.Tasks;

// Minimal job system: a queue plus work stealing.
public class JobSystem
{
    readonly ConcurrentQueue<Action>[] _queues;
    readonly System.Threading.CancellationTokenSource _stop = new();

    public JobSystem(int workers)
    {
        _queues = new ConcurrentQueue<Action>[workers];
        for (int i = 0; i < workers; i++) _queues[i] = new ConcurrentQueue<Action>();
        for (int i = 0; i < workers; i++)
        {
            int id = i;
            Task.Run(() => Worker(id), _stop.Token);
        }
    }

    public void Schedule(Action job) => _queues[0].Enqueue(job);

    void Worker(int id)
    {
        var own = _queues[id];
        while (!_stop.IsCancellationRequested)
        {
            if (own.TryDequeue(out var job))
            {
                try { job(); } catch (Exception e) { /* log it, do not kill the thread */ }
                continue;
            }
            // work stealing: take somebody else's job
            bool stole = false;
            for (int k = 1; k < _queues.Length; k++)
            {
                var other = _queues[(id + k) % _queues.Length];
                if (other.TryDequeue(out job)) { try { job(); } catch { } stole = true; break; }
            }
            if (!stole) System.Threading.Thread.Sleep(0);   // idle
        }
    }

    public void Dispose() { _stop.Cancel(); }
}

Memory: pools, GC and asset streaming

Memory: pools, GC and asset streaming

Memory is the one resource you cannot squeeze. You can optimise frame time, but you cannot optimise an out-of-memory crash — the game simply dies. So gameplay uses pools and arena allocators, and heavy assets are streamed on demand.

object poolsGCfragmentationstreamingvirtual texturing
01 Essence

Fragmentation is the main enemy: after thousands of small allocations and frees, large blocks no longer fit even though there is plenty free. Hence the rule for the hot path: allocate nothing in the game loop. Objects come from a pool, temporary arrays come from reusable buffers (arena/buffer pools) that grow as needed and reset in O(1).

In managed languages this is also about GC pauses. Even short pauses break control feel. The answers: allocate outside the frame (on the loading screen), use incremental GC, avoid allocations in input handlers, and adopt a generational approach — “hot” objects stay in generation 0 and are not promoted.

Assets are a separate story. Keeping the whole world in memory is impossible: 1000 4K textures at 32 MB each is 32 GB. Three mechanisms work: distance-based streaming (load a sector when the player is close, unload it when they are far), virtual texturing (virtual address → physical pages loaded on demand) and a memory budget with priorities (what to drop first). The unload strategy matters more than the load strategy: the player must never notice a texture disappearing.

the mathematical model
peak = resident + streamed + transient + fragmentation_slack, slack ≈ 10–20 % of the budget
Typical budgets: 4–8 GB of VRAM per game on PC, 1.5–3 GB on mobile, per class on consoles. Transient memory (frame buffers) is counted separately: it grows with the number of frames in flight.
02 How to build it
  1. Take a memory profile: resident (by type), transient and fragmentation — CPU and GPU separately.
  2. Remove every allocation from the hot path: pools for objects, reusable buffers for temporary data.
  3. Set a memory budget per level and per world sector; on overflow, unload by priority.
  4. Implement streaming with hysteresis: do not unload a resource if the player may return in a second.
  5. Watch the transient buffers: their count grows with the frames in flight (CPU and GPU together) and causes OOM on weak hardware.
  6. Test the behaviour under memory pressure: the game must degrade, not crash.
03 Working code

class Pool:
    """Object pool with no runtime allocations."""
    __slots__ = ("_free", "_factory", "_live")

    def __init__(self, factory, initial=0):
        self._factory = factory
        self._free = [factory() for _ in range(initial)]
        self._live = set()

    def acquire(self):
        if self._free:
            obj = self._free.pop()
        else:
            obj = self._factory()      # the only runtime allocation
        self._live.add(id(obj))
        return obj

    def release(self, obj):
        self._live.discard(id(obj))
        obj.reset()                   # reset the state, do not create a new one
        self._free.append(obj)

    @property
    def live_count(self):
        return len(self._live)

Portals and non-Euclidean geometry

Portals and non-Euclidean geometry

A portal is a transform of space: the camera sees the scene through a matrix that glues two places together. Portal recursion, clipping and correct physics all require careful handling of matrices and clip planes.

projective geometryquaternionsrecursion
01 Essence

A portal is defined by two rectangles (entry and exit) with normals. The view through a portal is a render with a transformed camera: M = Texit · Rexit · Rentry−1 · Tentry−1 (up to scale). Texture projection uses the same matrix; for recursion it is applied repeatedly, with a depth limit.

Geometrically this is a projective gluing: a space where two planes are identified by a transformation. Quaternions are convenient for orientation (no gimbal lock), but a general portal transform includes a reflection or rotation plus a translation. A mirror portal flips the orientation, which breaks triangle winding — so either avoid reflections or invert culling and normals.

The problems: clipping the geometry behind the portal (oblique near plane / clip plane) so you neither render too much nor see through the wall; recursion — rendering into a texture with a reduced resolution; physics — teleporting the object with a transformed velocity and angular momentum; and carrying the “camera” across. Topological gameplay (torus, Möbius)

Topological gameplay (torus, Möbius)

A torus is a rectangle with opposite edges identified: leave on the right and you enter on the left. A Möbius strip adds a flip when you walk around it, which breaks orientation — and therefore the usual navigation.

topologygluesEuler characteristic
01 Essence

The torus comes from gluing opposite sides of a square: (x, y) ~ (x + W, y) ~ (x, y + H). The implementation is modular arithmetic on coordinates plus “ghost” copies of objects near the edges for rendering and physics. Radii and neighbour queries must account for the wrap, otherwise projectiles vanish at the edge and the AI cannot see an enemy “through the wall”.

The Möbius strip is a glue with a flip: (0, y) ~ (1, 1 − y). Walking along the strip returns you to the same point with a flipped orientation; after two laps you are back to normal. That means non-orientability: there is no global “up” and “down”, and local coordinates have to be carried across the seam with a flip matrix. For the player it is a puzzle; for the code it is a source of bugs in normals and cameras.

Topological invariants help the design: the Euler characteristic χ = V − E + F (torus: 0, sphere: 2, Klein bottle: 0) and the genus g = (2 − χ)/2. For gameplay this means constraints on cuts and glues: you cannot cut a torus into a sphere without changing the topology — and that can be a mechanic (as in some puzzle games).

the mathematical model
Torus: (x, y) ~ (x mod W, y mod H), Möbius: (0, y) ~ (1, 1 − y)
χ = V − E + F; g = (2 − χ)/2 for a closed orientable surface. Torus: χ = 0, g = 1.
02 How to build it
  1. Choose the world representation: modular coordinates or explicit seam portals.
  2. Implement the wrap for positions, velocities, queries and rendering (ghost copies).
  3. For the Möbius strip, add an orientation transfer matrix when crossing the seam.
  4. Test the camera, lighting and physics at the seams — that is where orientation breaks.
  5. Keep it simple: the more seams there are, the harder it is to debug and to explain to the player.

Entanglement as a game mechanic

Entanglement as a game mechanic

Entanglement is a correlation that cannot be explained by local hidden variables. For a game it is a “paired object” mechanic: the state of one instantly determines the measurement result of the other — but no information can be transmitted.

tensor algebraHilbert spaceBell
01 Essence

The state of two qubits lives in the tensor product of the spaces: |ψ⟩ = α|00⟩ + β|01⟩ + γ|10⟩ + δ|11⟩. An entangled state cannot be factored into |a⟩⊗|b⟩; the canonical example is Bell's singlet (|01⟩ − |10⟩)/√2. The density matrix ρ = |ψ⟩⟨ψ|, and taking the partial trace yields a mixed state for one qubit — which is exactly why it looks random locally.

The key fact: measuring one qubit in the Z basis gives 0 or 1 with equal probability, but the result of the other is perfectly correlated (for the singlet, opposite). Measuring at different angles gives a correlation of −cos θ, violating Bell's inequality (CHSH: |S| ≤ 2 classically, up to 2√2 quantumically). For gameplay this becomes a puzzle: “tune the measurement basis to get the correlation you need”.

Design: entangled pairs as “linked objects” — an enemy and its shadow, two locks, a door and a bridge. The player cannot send a message but can exploit correlations if they know the basis. Always explain the rules in the language of mechanics rather than physics, and never give the player instant communication — that breaks both the physics and the balance.

the mathematical model
|Φ⁺⟩ = (|00⟩ + |11⟩)/√2, E(a,b) = −cos(a−b), |S| ≤ 2√2
CHSH: S = E(a,b) − E(a,b′) + E(a′,b) + E(a′,b′). The classical limit is 2, the quantum limit 2√2 ≈ 2.828.
02 How to build it
  1. Define the entangled pairs and what exactly correlates (state, damage, position).
  2. Provide the measurement bases the player can choose (angles, tools).
  3. Implement measurement as a probabilistic draw with the −cos θ correlation.
  4. Forbid information transfer: the second result is only known after the first is measured.
  5. Check the balance: correlations must not offer a free shortcut through the level.

def bell_correlate(a_angle, b_angle, rng=random):
    """Returns a pair of outcomes with the correlation E = -cos(a - b)."""
    p_same = (1.0 - math.cos(a_angle - b_angle)) / 2.0
    a = 0 if rng.random() < 0.5 else 1
    # for a singlet: equal outcomes are rare at a small angle
    b = a if rng.random() < p_same else 1 - a
    return a, b

Chaos, bifurcations and attractors

Chaos, bifurcations and attractors

Chaos is sensitivity to initial conditions in a deterministic system. The logistic map and the Lorenz attractor are the canonical models, and the Lyapunov exponent measures how fast nearby solutions diverge.

chaos theoryattractorsLyapunov exponent
01 Essence

The logistic map: xn+1 = r·xn(1 − xn). Below r = 3 there is a stable fixed point, between 3 and 3.57 a cascade of period doubling, and beyond that chaos with windows of order. The bifurcation diagram is a beautiful, understandable UI tool: the player moves r and watches the behaviour change.

The Lorenz attractor: dx/dt = σ(y − x), dy/dt = x(ρ − z) − y, dz/dt = xy − βz. The trajectory never repeats but stays in a bounded region (a strange attractor) and has a fractal dimension. For visuals, fading 3D lines are enough; for gameplay, it is a “chaotic” source of motion that still stays bounded.

The Lyapunov exponent λ > 0 means exponential divergence: δ(t) ≈ δ₀·eλt. The practical consequence: chaotic systems cannot be predicted over a long horizon without enormous precision. In multiplayer that is fatal for determinism; in a single-player game it is a source of uniqueness. Use chaos deliberately: for background effects, never for critical simulation.

the mathematical model
xn+1 = r·xn(1 − xn), λ = lim (1/n)·Σ ln|f′(xᵢ)|
Lorenz: σ = 10, ρ = 28, β = 8/3. λ > 0 means chaos; for Lorenz λ ≈ 0.9.
02 How to build it
  1. Pick the map/system and the parameter the player will change.
  2. Build a bifurcation diagram or a phase portrait to tune it.
  3. Estimate the Lyapunov exponent and the horizon of predictability.
  4. Visualise the trajectories with fading and colour by time.
  5. Never use chaos for critical networked physics; for effects, bound the amplitude.

def logistic(r, x0=0.5, n=1006, skip=100):

def lyapunov(r, x0=0.5, n=2006, skip=200):
    x, total = x0, 0.0
    for i in range(n + skip):
        x = r * x * (1 - x)
        if i >= skip:
            d = abs(r * (1 - 2 * x))
            total += math.log(d) if d > 1e-12 else -30
    return total / n          # > 0 means chaos

def lorenz_step(p, dt=0.01, sigma=10, rho=28, beta=8/3):
    x, y, z = p
    dx = sigma * (y - x)
    dy = x * (rho - z) - y
    dz = x * y - beta * z
    return (x + dx*dt, y + dy*dt, z + dz*dt)

Weapon balance analysis (regression, ANOVA)

Weapon balance analysis (regression, ANOVA)

Weapon balance is not checked by eye but with metrics: time to kill, DPS adjusted for misses, win rate and pick rate. Regression shows which characteristics actually predict strength.

regressionANOVATTK
01 Essence

Theoretical weapon strength: TTK = HP/(damage × fire rate) adjusted for reloads and misses. Effective DPS = damage·RPM/60·accuracy/(1 + reload_time/engagement_time). But the key metric is not the number in a spreadsheet — it is the outcome: the weapon's win rate with the player's skill controlled (for example, per rank).

Regression: winrate ~ β₀ + β₁·dps + β₂·accuracy + β₃·range + ε. The coefficients show which attribute outweighs the others. ANOVA compares groups (weapons, classes) and tests whether the differences are significant at all or just sampling noise. Always compute confidence intervals: with 500 matches a 2 % win-rate difference may be indistinguishable from chance.

Pick rate is the most important metric: if a weapon is taken in 60 % of matches and wins 52 %, it dominates. The feedback loop: do not nerf the damage number — nerf what makes the weapon unavoidable (versatility, the lack of counter-picks). And test changes on simulations and bots before shipping, or balance patches become a lottery.

the mathematical model
TTK = HP / (DPS·accuracy), DPS = damage·RPM/60 / (1 + reload/engagement)
Regression: y = Xβ + ε; ANOVA: F = MSbetween/MSwithin, p < 0.05 means the difference is significant.
02 How to build it
  1. Define the metrics: TTK, effective DPS, win rate, pick rate, survival.
  2. Collect per-match data with skill controlled (rating or rank).
  3. Fit the regression and test the significance of the coefficients.
  4. Compare groups with ANOVA and confidence intervals.
  5. Change one parameter per patch and measure the effect on win rate and pick rate.

Matchmaking with Elo, Glicko-2 and TrueSkill

Matchmaking with Elo, Glicko-2 and TrueSkill

Matchmaking solves two problems: estimating a player's strength and assembling a match with equal chances. Elo is simple but unstable; Glicko-2 and TrueSkill model uncertainty and team play.

EloGlicko-2TrueSkillBayesian
01 Essence

Elo: expected result E = 1/(1 + 10(Ropp−R)/400), update R′ = R + K(S − E). Problems: K is fixed, uncertainty is not modelled, and a newcomer and a veteran with the same rating are treated as equal. Even so, Elo works excellently as a rating “currency” and players understand it.

Glicko-2 adds a rating deviation (RD) and volatility: after a long break the RD grows and the rating moves faster — the system “re-checks” the player. TrueSkill is a Bayesian model for teams: a player's strength is a Gaussian N(μ, σ²), updated by Bayes' rule, and the matchmaker minimises the expected unfairness (the draw probability).

In practice the matchmaker optimises more than equal strength: wait time, region, group size, role order. It usually uses an expanding search range and treats match “quality” as a function of the spread of ratings. Smurfs and boosting are a separate problem: you need fast calibration matches and anomaly detection on progress.

the mathematical model
E = 1/(1 + 10(Rb−Ra)/400), R′ = R + K(S − E)
TrueSkill: match quality = 2·Φ(μdiff/√(2β² + σa² + σb²)), where β is the “luck scale”.
02 How to build it
  1. Choose the rating model: Elo for simplicity, Glicko-2 or TrueSkill for accuracy.
  2. Define the format: 1v1, teams, roles, group size.
  3. Set the match-quality function and the weights for wait time and region.
  4. Implement the expanding search and smurf protection (calibration, detection).
  5. Monitor the rating distribution, search time and the share of unfair matches.

Time-series forecasting (ARIMA, seasonality)

Time-series forecasting (ARIMA, seasonality)

Player and sales trends are time series with a trend, seasonality and noise. ARIMA models the autocorrelation, and seasonality captures weekly and event-driven spikes.

ARIMAseasonalityanomalies
01 Essence

Stationarity is the key condition. A series with a trend is differenced: Δyₜ = yₜ − yₜ₋₁. AR(p) describes the dependence on past values, MA(q) on past errors; ARIMA(p,d,q) combines them. Seasonality enters through seasonal differencing: SARIMA(p,d,q)(P,D,Q)s with s = 7 (days of the week) or 24 (hours).

Useful game metrics: DAU/MAU, D1/D7/D30 retention, conversion, ARPPU, session length. Spikes from events and updates break the model — they must be pulled out into separate regressors or flagged as anomalies, otherwise the forecast gets smeared. Taking logs stabilises the variance of multiplicative series.

Validation is strictly temporal, never a random split: train on the past, test on the future. Metrics: MAE, RMSE, MAPE — and above all business value (an error in a capacity forecast costs more than an error in a content forecast). Simple baselines (naive, seasonal-naive) often beat complex models, so always compare.

the mathematical model
ARIMA(p,d,q): (1 − ΣφᵢLⁱ)(1−L)dyₜ = (1 + ΣθⱼLʲ)εₜ
L — the lag operator. SARIMA adds seasonal polynomials with period s. MAPE = (100/n)·Σ|y − ŷ|/|y|.
02 How to build it
  1. Build the series and check stationarity (differencing, ADF test).
  2. Choose p and q from ACF/PACF or information criteria (AIC).
  3. Add seasonality and regressors for events and updates.
  4. Validate temporally and compare against baselines.
  5. Watch for model drift and retrain on a schedule.

Loot systems (Pareto, CLT, pity)

Loot systems (Pareto, CLT, pity)

Loot is a reward distribution with a long tail. Pareto models “the rich get richer”, the central limit theorem covers the total loot over a series, and pity mechanics bound the worst case.

Pareto distributionCLTpity
01 Essence

The Pareto distribution: P(X > x) = (xm/x)α. Small α gives a heavy tail: most rewards are cheap, rare ones are very expensive. For loot that is a natural model — 90 % of drops are junk, 1 % are legendaries. But a pure Pareto can hand a jackpot in the first minute and break progression, so the tail is truncated and guarantees are added.

The central limit theorem: the sum of independent identically distributed variables tends to a normal distribution. So the total loot over N openings is predictable (mean N·μ and variance N·σ²) even when the individual drops are Pareto (given finite variance). That lets you design a “reward budget” per session and check that the player stays on the progression curve.

Pity and guarantees: “at most N attempts until the rare drop”, “the first 10 openings have a boosted chance”, “duplicates convert into currency”. These reduce the perceived variance but change the maths: the effective probability becomes conditional and has to be computed honestly. In many countries disclosing the odds is legally required — design the system so it can be explained to the player.

the mathematical model
P(X > x) = (xm/x)α, Σi=1..NXᵢ ≈ N(N·μ, N·σ²)
Pity: P(success on k) = p for k < N; 1 for k = N. Expected attempts = (1 − (1−p)N)/p.
02 How to build it
  1. Define the rarities, base chances and item weights inside each rarity.
  2. Model the value distribution of the loot (Pareto / log-normal).
  3. Add pity and guarantees, then recompute the effective chances.
  4. Check the budget: how many rewards does a player get per hour or session?
  5. Publish the odds and add protection against a dry streak.

Visibility: PVS, portals, BSP

Visibility: PVS, portals, BSP

Visibility is the culling of what does not reach the frame or is hidden. BSP splits space with planes, portals cull by room, PVS pre-computes “what is visible from this cell”.

BSPPVSocclusion culling
01 Essence

A BSP tree recursively splits space with planes (usually along geometry faces). It gives a correct front-to-back draw order and lets you cull whole subtrees quickly. In Quake the BSP was the backbone of rendering and collision. The downside is statics: any geometry change means a rebuild.

PVS (potentially visible set): space is divided into leaves and for every leaf the list of visible leaves is computed ahead of time. At runtime you draw only those. It is a classic BSP-era technique and still used in modern engines as precomputed visibility. Portals are a different approach: rooms are connected by portals, and if the chain of portals misses the frustum, the whole room is culled.

The modern stack: frustum culling (by AABB), occlusion culling (hierarchical depth buffer, hardware occlusion queries), LOD and HLOD. Ricochet and reflection vectors

Ricochet and reflection vectors

The ideal ricochet reflects the velocity about the normal: v′ = v − 2(v·n)n. A realistic one loses energy, adds spread and has a “no ricochet” condition that depends on the angle and the material.

reflectionSnell's lawrandomness
01 Essence

The reflection formula works for a perfectly elastic impact. In reality energy is lost: v′ = e·(v − 2(v·n)n), where e is the coefficient of restitution (0.3–0.9). Bullets also lose speed and get a deviation that depends on the roughness of the surface. At a shallow (grazing) angle a bullet ricochets more often; at a steep angle it deforms and lodges.

The ricochet criterion is the angle between the velocity and the normal. If |v·n|/|v| < cos(θcrit) it ricochets, otherwise it hits. θcrit depends on material and speed: roughly 5–15° for steel, 10–20° for concrete, more for armour. That is a cheap and believable model for shooters.

After the reflection the ray keeps living: you need a bounce limit, a trace of the next segment and decay. Visually, draw a tracer per segment with a temporal fade. For gameplay, ricochet prediction (bounce off a wall into a target) can be a separate mechanic — and then the criterion and the spread must be deterministic, otherwise the player cannot learn it.

the mathematical model
v′ = v − 2(v·n)·n, with loss: v′ = e·(v − 2(v·n)·n)
Ricochet condition: |v·n|/|v| < cos θcrit. For refraction (Snell): n₁sinθ₁ = n₂sinθ₂.
02 How to build it
  1. Trace the ray, find the surface normal and the material.
  2. Check the ricochet criterion against the angle and the surface type.
  3. Reflect the velocity and scale its magnitude by the coefficient of restitution.
  4. Add a small random spread plus the tracer or effect.
  5. Repeat until the bounce limit is reached or the energy is gone.

import math, random

def reflect(v, n, restitution=0.75):
    dot = v[0]*n[0] + v[1]*n[1] + v[2]*n[2]

Voxel worlds and marching cubes

Voxel worlds and marching cubes

A voxel world is a grid of density values. The surface is extracted with marching cubes (a polygon mesh) or rendered directly with ray marching; storage uses an octree or flat chunks.

marching cubesSDFoctree
01 Essence

Marching cubes: a 2×2×2 cubic cell is sampled, the 256 sign combinations map to a table of edges and triangles. Vertices are interpolated by density, which gives a smooth surface. The algorithm is simple and parallelises well, but it produces many triangles and struggles with thin features (marching tetrahedra solves the diagonal connectivity problem).

An SDF (signed distance field) is more convenient for editing: f(x) < 0 inside, > 0 outside. Union is min(f₁, f₂), subtraction is max(f₁, −f₂), a smooth union is a smooth min. Editing the world becomes composing functions instead of rebuilding the grid. Render with ray marching over the SDF; for physics use a marching-cubes mesh or an approximation.

Storage: 32³ chunks in flat arrays with an octree for LOD, a block palette instead of full descriptions, a mesh cache and deferred rebuilds of only the changed chunks. For large worlds the critical parts are background generation, streaming, compression (RLE) and a cap on the triangles per frame. Meshing a 32³ chunk takes milliseconds — enough for interactive editing.

the mathematical model
SDF: f(x) < 0 inside, f(x) = 0 on the surface; union = min(f₁, f₂)
Vertex interpolation: p = p₁ + (0 − f₁)/(f₂ − f₁)·(p₂ − p₁). An octree gives LOD with a step of 2l.
02 How to build it
  1. Choose the representation: blocks (Minecraft) or SDF density (Teardown/Claybook).
  2. Build the density function or palette and split the world into chunks.
  3. Extract the mesh with marching cubes and interpolated vertices.
  4. Cache the meshes, rebuild only changed chunks and add LOD.
  5. Stream the chunks around the player and compress the data (RLE / palette).

Procedural textures (noise, FFT, weathering)

Procedural textures (noise, FFT, weathering)

A procedural texture is a function of coordinates, not a picture. Noise, Voronoi cells and convolutions give you wood, metal and stone; the price is shader compute and the fight against visible tiling.

noiseFourier transformtiling
01 Essence

The basic building blocks: value/Perlin/simplex noise, Voronoi cells (F1/F2 — distances to the nearest points), gradients and waves. Composition is blending through masks: stone = fBm + Voronoi cracks, wood = growth rings from the distance plus fibre noise, metal = an almost uniform albedo plus roughness from noise.

Tiling: periodic noise (sampling modulo the period) gives seamlessness. The advanced version is “tileable” generation via FFT: generate the spectrum, filter it and inverse-transform — the result is periodic by construction. To kill visible repetition, use domain warping, several scales and stochastic tiling (texture bombing).

PBR: albedo, normal, roughness, metallic. Normals can be generated from a height map (Sobel), roughness from noise and dirt masks, AO from height or an SDF. The compute cost in the shader is the problem: 3D noise per pixel is expensive, so textures are usually baked into atlases offline and the runtime only blends layers through masks.

the mathematical model
fBm = Σ gaini·noise(freq·lacunarityi·x), Voronoi: F1 = min|x − pᵢ|

  1. Define the material: which layers and masks you need (stone, dirt, scratches).

Screen-space distortion with complex numbers

Screen-space distortion with complex numbers

Screen distortion is a UV mapping. Complex functions give beautiful conformal effects (they preserve angles), while noise and fields add motion. The main rule: do not break the readability of the interface.

complex numbersconformal mapsUV
01 Essence

The complex plane: z = u + iv, the map w = f(z). Conformal functions (w = z², w = ez, w = 1/z) preserve angles locally — which is why they “look right”, like lenses and whirlpools. The inversion 1/z gives a black hole, the exponential gives a swirl, the power zn gives n-ray distortions.

In practice you sample the scene not at UV but at f(UV + offset). You have to limit the affected area (a radial mask) so the whole screen does not warp, and protect the UI — the interface is rendered after the distortion or on a separate layer. For animation, use time as a parameter and noise as a phase offset.

Side effects: edge blur (sampling outside [0,1] produces artefacts — clamp or wrap), chromatic aberration (offset the channels), vignette. For “magic” and portals, add brightness and colour in the centre, otherwise the effect reads as a bug. And always ship an option to turn the distortion off for accessibility.

the mathematical model
w = f(z), z = u + iv, lens: w = z + k·zm, swirl: w = z·ei·θ(r)
θ(r) = a·e−r²/σ². Inversion: w = c/z gives a “black hole” with radial stretching.
02 How to build it
  1. Define the centre, radius and strength of the distortion; build the mask.
  2. Choose the function (lens, swirl, inversion) and the animation parameters.
  3. Offset the UV with clamping and protection against leaving the screen.
  4. Add chromatic aberration and a glow for readability.
  5. Render the UI after the effect and provide a switch to disable it.

vec2 lens(vec2 uv, vec2 center, float radius, float strength) {
    vec2 d = uv - center;
    float r = length(d);
    float m = 1.0 - smoothstep(radius * 0.6, radius, r);
    float k = strength * m * m;
    return uv - d * k * (r / radius);
}

// a swirl on the complex plane: w = z * exp(i * theta(r))
vec2 swirl(vec2 uv, vec2 center, float strength, float time) {
    vec2 d = uv - center;
    float r = length(d);
    float a = strength * exp(-r * r * 8.0) + time;
    float s = sin(a), c = cos(a);
    vec2 rot = vec2(d.x * c - d.y * s, d.x * s + d.y * c);
    return center + rot;
}

Optics: diffraction, BRDF, dispersion

Optics: diffraction, BRDF, dispersion

Optics in games means models of reflection and refraction. The BRDF says how much light leaves towards the camera, while diffraction and dispersion add rainbows and halos around light sources.

FresnelBRDFdiffraction
01 Essence

The microfacet BRDF (Cook–Torrance): f = D·G·F/(4·(n·l)(n·v)), where D is the distribution of micro-normals (GGX), G the shadowing term, and F the Fresnel term (Schlick: F = F₀ + (1−F₀)(1−cosθ)⁵). Energy conservation requires f to satisfy ∫ f·cosθ dω ≤ 1; otherwise the material glows.

Refraction follows Snell's law: n₁sinθ₁ = n₂sinθ₂. Dispersion means n depends on the wavelength: render three channels with different indices (or more for spectral rendering). That gives rainbow caustics and prismatic effects. A full spectral solution is expensive, but three channels are usually enough.

Diffraction and glow: the Fresnel integral describes edge diffraction, but in games it is replaced by bloom (a convolution), lens flares and artist-driven halos. Wave optics is only needed for scientific visualisation. For photorealism, correct exposure, tonemapping and colour temperature matter far more than accurate diffraction.

the mathematical model
f = D·G·F / (4·(n·l)(n·v)), F = F₀ + (1−F₀)(1−cosθ)⁵, n₁sinθ₁ = n₂sinθ₂
GGX: D = α²/(π·((n·h)²(α²−1)+1)²). Dispersion: n(λ) — different indices for R/G/B.
02 How to build it
  1. Choose a BRDF for the materials: GGX plus Schlick for metals and dielectrics.
  2. Tune F₀ (0.04 for dielectrics, the albedo for metals).
  3. Add refraction with dispersion for glass and water if you need it.
  4. Do bloom, flares and tonemapping so light sources stay readable.
  5. Verify energy conservation and that materials do not “glow” in shadow.

Auction design and market clearing

Auction design and market clearing

An auction is a rule for allocation and price. A second-price (Vickrey) auction encourages truthful bidding, and a double auction converges to the equilibrium of demand and supply.

Vickrey auctionequilibriummarket
01 Essence

The Vickrey auction (second-price sealed bid): the highest bidder wins but pays the second-highest bid. The dominant strategy is to bid your true value — overbidding does not increase the payoff, underbidding risks losing. For a game market this is the best choice when you want an honest allocation of rare items without last-second sniping.

A double auction: buyers and sellers submit orders and trades happen where the prices cross. The equilibrium price is where the demand and supply curves meet. In games this becomes an order book matched by price-time priority. The subtleties are the minimum price step, fees and protection against manipulation (wash trading, order spam).

A sealed first-price auction is theoretically equivalent in expected revenue (the revenue equivalence theorem) but is strategically harder: you have to shade your bid. For players that is opaque, so game design usually picks Vickrey or an English auction. Transparency of the rules matters more than mathematical elegance.

the mathematical model
Vickrey: winner = argmax bᵢ, pays maxj≠i bⱼ. Double auction: a trade when bbuy ≥ asell
Expected revenue in a first-price auction with n bidders and uniform values: (n−1)/n · vmax.
02 How to build it
  1. Pick the format: Vickrey, English, double auction or instant buy.
  2. Define the price step, the fee and anti-sniping (extend the timer on a late bid).
  3. Implement an order book with price-time matching.
  4. Add manipulation protection and per-player limits.
  5. Log the trades and build price indices to monitor inflation.

import heapq

def vickrey(bids):
    """bids: [(player, value)] -> (winner, price)."""
    ordered = sorted(bids, key=lambda b: b[1], reverse=True)
    winner = ordered[0][0]
    price = ordered[1][1] if len(ordered) > 1 else 0.0
    return winner, price

class OrderBook:
    def __init__(self):
        self.bids, self.asks = [], []      # max-heap / min-heap

    def add_bid(self, price, qty, owner):
        heapq.heappush(self.bids, (-price, owner, qty))

    def add_ask(self, price, qty, owner):
        heapq.heappush(self.asks, (price, owner, qty))

    def match(self):
        trades = []
        while self.bids and self.asks and -self.bids[0][0] >= self.asks[0][0]:
            bp, buyer, bq = heapq.heappop(self.bids)
            ap, seller, aq = heapq.heappop(self.asks)
            qty = min(bq, aq)
            trades.append((buyer, seller, -bp, ap, qty))
            if bq > qty: heapq.heappush(self.bids, (bp, buyer, bq - qty))
            if aq > qty: heapq.heappush(self.asks, (ap, seller, aq - qty))
        return trades

Resource allocation and optimal control

Resource allocation and optimal control

Resource allocation is an optimisation problem: maximise value under constraints. Linear programming gives the exact answer, while priorities and greed give a fast version the player can understand.

optimal controlLPpriorities
01 Essence

The classic problem: a base has N resources, M units and K buildings; you have to assign workers to maximise production or minimise time to goal. Formally this is an LP: max Σ vᵢxᵢ subject to resource and building constraints. The simplex method solves it in polynomial time; for small problems brute force and greed are enough.

Optimal control adds time: u(t) is the control, x′(t) = f(x, u) the dynamics, J = ∫ L(x, u)dt the cost. For games that is usually too abstract; in practice you use MPC (model predictive control): at every step solve the problem over a horizon H and apply only the first control. That is robust to change and understandable to a designer.

For gameplay, transparency matters most: the player must understand why a worker went to the mine and not to the forest. Priorities (hunger > production > construction), reserves and “soft” constraints read better than a hidden optimiser. The ideal split is LP for an AI advisor, not for automatic control: the player decides, the system suggests.

the mathematical model
max Σ vᵢxᵢ s.t. Σ aᵢⱼxⱼ ≤ bᵢ, x ≥ 0
The dual problem gives the “shadow prices” of the resources — a great UI hint: what does one unit of wood cost right now.
02 How to build it
  1. Describe the variables, the constraints and the objective function.
  2. Solve the LP (simplex) or apply a greedy algorithm with priorities.
  3. Add time and dynamics (MPC with a horizon) if needed.
  4. Show the player the shadow prices and priorities, not just the result.
  5. Test the edge cases: hunger, missing resources, full warehouses.

def greedy_allocate(workers, jobs, priority):
    """jobs: [(name, need_workers, value)] -> the allocation."""
    plan, left = {}, workers
    for name, need, value in sorted(jobs, key=priority, reverse=True):
        take = min(need, left)
        if take:
            plan[name] = take
            left -= take
        if left == 0:
            break
    return plan, left

In-game inflation and monetary sinks

Inflation in a game is the growth of the money supply without a growth in goods. The equation of exchange MV = PQ links money, velocity, prices and volume; the cure is sinks (taxes, repairs, consumables), not only a nerf to drops.

01 Essence

The equation of exchange: M·V = P·Q. If the money supply M grows while volume Q and velocity V stay the same, prices P rise. In a game M grows from drops and quests, V from how often players spend, Q from production. Inflation feels like “everything is expensive and earning is easy”; deflation like “nothing to buy, money piles up”.

Sinks: taxes, auction fees, repairs, consumables, crafting with a failure chance, rent, and “burning” currency on cosmetics. The sink has to scale with wealth: a fixed repair price will not slow down a millionaire. A progressive wealth tax and a turnover fee work better.

Monitoring: a price index (a basket of typical goods), M2 (the total currency in the economy), the share of currency held by the top 1 % of players, and the velocity of money. If the index grows faster than new players' income, the economy is closing itself to newcomers. Adjust gently: event sinks, seasonal collections, new goods — not a sudden nerf that devalues the players' work.

the mathematical model
M·V = P·Q, π ≈ ΔM/M + ΔV/V − ΔQ/Q
π — the inflation rate. With ΔM = 10 %, ΔV = 0, ΔQ = 4 %, we get π ≈ 6 %.
02 How to build it
  1. Identify M (all currency sources) and Q (the volume of goods and services).
  2. Introduce sinks that scale with wealth rather than fixed amounts.
  3. Build a price index over a basket and track it.
  4. Add seasonal sinks and new goods as soft regulators.
  5. Watch the gap between newcomers and veterans; even out the income.

Spatial audio and HRTF

Spatial audio and HRTF

3D sound rests on two cues: the interaural time difference and the interaural level difference. HRTF adds the shape of the ear, and spherical harmonics encode the sound field efficiently.

HRTFITD/ILDspherical harmonics
01 Essence

ITD (interaural time difference) reaches 0.7 ms between the ears; ILD (level difference) reaches 20 dB at high frequencies, where the head shadows the sound. The brain combines them with spectral cues from the pinna to determine not only azimuth but also elevation. Without an HRTF, “left/right” is audible but “above/below” barely is.

An HRTF is the transfer function from a source to the eardrum: y(t) = h(t) * x(t), where h depends on the direction. It is measured on a head-and-torso simulator (KEMAR) or simulated. Convolving per source is expensive, so in practice you use a set of 16–32 directions with interpolation, or Ambisonics panning.

First-order Ambisonics (four channels: W, X, Y, Z) encodes the field with spherical harmonics; decoding to headphones or speakers yields a scene that rotates with the head. For VR this is the standard: the sound is anchored to the world and turns with you. Reverb zones, occlusion (a sound behind a wall is duller) and distance attenuation (1/r) complete the picture.

the mathematical model
ILD ≈ 20·log₁₀(rfar/rnear), y = h(θ,φ) * x
Ambisonics: B-format W = p/√2, X = p·cosθcosφ, Y = p·sinθcosφ, Z = p·sinφ.
02 How to build it
  1. Choose the renderer: stereo panning, Ambisonics or HRTF convolution.
  2. Implement distance attenuation and air absorption of high frequencies.
  3. Add occlusion and obstruction through a raycast and a low-pass filter.
  4. Set up reverb zones and voice priorities (voice limiting).
  5. Test on headphones and speakers; offer options for hard-of-hearing players.

import math

SPEED_OF_SOUND = 343.0
HEAD_WIDTH = 0.18

def itd_ild(azimuth_deg, distance=2.0):
    """A simple model: the delay and the level difference between the ears."""
    theta = math.radians(azimuth_deg)
    path_diff = HEAD_WIDTH * math.sin(theta)
    itd = path_diff / SPEED_OF_SOUND          # seconds
    ild_db = 20.0 * math.log10(max(1e-3, (distance - path_diff/2) /
                                        (distance + path_diff/2)))
    return itd, ild_db

def distance_gain(distance, ref=1.0, rolloff=1.0):
    return ref / (ref + rolloff * max(0.0, distance - ref))

def air_absorption(freq_hz, distance_m):
    # simplified: high frequencies die away faster
    return math.exp(-distance_m * (0.001 + freq_hz * 2e-6))

Physical modeling synthesis (Karplus–Strong, waveguide)

Physical modeling synthesis (Karplus–Strong, waveguide)

A string is a delay line with a filter in the feedback path. The Karplus–Strong model gives you a guitar in six lines of code, and digital waveguides cover winds and bowed strings with resonances.

waveguideFIR filtersresonance
01 Essence

Karplus–Strong: fill a ring buffer with noise (the excitation), then each step compute y[n] = 0.5·(y[n−N] + y[n−N−1])·decay. This is the simplest waveguide: the delay N = sample_rate/frequency, the averaging is a low-pass filter, and decay is the loss. The result sounds remarkably like a plucked string.

A digital waveguide: a delay line with a loss filter and a nonlinearity at the end. For winds — the nonlinearity is the valve and there is a resonator; for bowed strings — the friction of the bow against the string. The extension: several parallel waveguides for the body, resonant filters for wood and metal.

Advantages over samples: infinite variation, small size, real-time response to parameters (pluck strength, position, length). Disadvantages: hard to tune the timbre, expensive with hundreds of voices, artefacts at extreme parameters. In games a hybrid is common: samples for the base notes, physical modelling for the variations.

the mathematical model
y[n] = 0.5·(y[n−N] + y[n−N−1])·d, N = fs/f₀
Waveguide: y[n] = x[n] + g·H(y[n−N]), where H is the loss filter and g the feedback gain (stable when |g·H| < 1).
02 How to build it
  1. Set the frequency, the string length and the loss coefficient.
  2. Implement the delay line with interpolation for an accurate frequency.
  3. Add the excitation (noise/impulse) and the nonlinearity for the pluck.
  4. Tune the body resonances and the stereo placement.
  5. Limit the number of voices and add anti-aliasing and parameter smoothing.
03 Working code
Python 
import random

def karplus_strong(freq, duration, sample_rate=44100, decay=0.996):
    n = int(sample_rate / freq)
    buffer = [random.uniform(-1, 1) for _ in range(n)]
    out, idx = [], 0
    prev = 0.0
    for _ in range(int(duration * sample_rate)):
        cur = buffer[idx]
        out.append(cur)
        # a low-pass filter plus the losses
        new = 0.5 * (cur + prev) * decay
        buffer[idx] = new
        prev = cur
        idx = (idx + 1) % n
    return out

# 220 Hz, 2 seconds - a recognisable plucked string
samples = karplus_strong(220.0, 2.0)

GANs for game content

GANs for game content

A GAN is a contest between a generator and a discriminator. The generator produces content, the discriminator tells it apart from the real thing, and training moves both towards an equilibrium where the fake is indistinguishable.

GANWassersteinbackprop
01 Essence

The minimax objective: minG maxD E[log D(x)] + E[log(1 − D(G(z)))]. In practice it is unstable: too strong a discriminator and the generator's gradients vanish. Wasserstein GAN replaces the logarithms with the Wasserstein distance (the earth mover's distance) and requires D to be 1-Lipschitz (weight clipping or a gradient penalty). Training becomes stable and the metric meaningful.

In games GANs are used for: texturing (pixel-art tiles, materials), level generation (raw maps → playable after post-processing), NPC portraits, data augmentation. The hard part is control: a plain GAN gives no guarantee that the generated level is completable or that the character does not have six fingers. So you add conditioning (cGAN), post-validation with rules, and rejection.

Alternatives and hybrids: diffusion models give better quality and control but cost more at inference; VAEs are faster but blurrier; for tiles, procedural rules plus a GAN for stylisation often suffice. Metrics: FID (distribution similarity), visual review and above all the share of samples that pass the game's validation.

the mathematical model
minGmaxD Ex[log D(x)] + Ez[log(1 − D(G(z)))]
WGAN: max‖f‖L≤1 E[f(x)] − E[f(G(z))]. Gradient penalty: λ·(‖∇x̂f(x̂)‖₂ − 1)².
02 How to build it
  1. Define the content and the quality metric (visual plus gameplay validity).
  2. Collect the dataset and train a baseline (DCGAN / WGAN-GP).
  3. Add conditioning (class, style, level parameters).
  4. Build rule-based post-validation and rejection.
  5. Evaluate FID and the share of valid samples; do not chase FID at the cost of playability.

def gradient_penalty(D, real, fake, lambda_=10.0):
    alpha = torch.rand(real.size(0), 1, 1, 1)
    mixed = (alpha * real + (1 - alpha) * fake).requires_grad_(True)
    grad = torch.autograd.grad(D(mixed).sum(), mixed, create_graph=True)[0]

Real-time upscaling (DLSS/FSR/XeSS)

Real-time upscaling (DLSS/FSR/XeSS)

Upscaling renders the frame at a lower resolution and reconstructs the high-resolution one using the history of previous frames and motion vectors. Neural methods give the best quality but need tensor cores; classical methods are cheaper and work everywhere.

convolutional networkstransformersTAA
01 Essence

The foundation is temporal accumulation (TAA): each frame is jittered sub-pixel, the history is accumulated and unconfident pixels are rejected using motion vectors. Plain averaging smears; you need a neighbourhood clamp, history in YCoCg and a response to scene changes (disocclusion). Upscaling is TAA with upsampling and a smarter reconstruction of detail.

Neural methods (DLSS, XeSS) use convolutional or transformer networks trained on the pair “low resolution + history → high resolution”. They recover high-frequency detail better than heuristics, but they need tensor cores (or DP4a) and a model trained for the specific engine. FSR is a spatial/temporal algorithm without ML and runs on any GPU.

The problems: ghosting (trails from the history), shimmering (flickering thin detail) and disocclusion (an object appeared and the history is invalid). Metrics are not only PSNR but temporal stability and detail preservation; you test by eye on grass, fences and wires. And there is always a native rendering fallback plus a sharpness setting, otherwise the picture ends up mushy.

the mathematical model
out = Σ w(t)·history(t) / Σ w(t), w depends on motion, depth, luminance
Jitter: Halton(2,3) sub-pixel offsets. Reprojection: uv′ = prev_view_proj · world_pos.
02 How to build it
  1. Render the frame at a low resolution with a sub-pixel jitter.
  2. Generate motion vectors and a depth buffer.
  3. Reproject the history and reject the invalid pixels (disocclusion).
  4. Blend history and current frame with confidence weights.
  5. Upscale (spatial or neural) and add a sharpness pass.
03 Working code
GLSL 
vec3 temporalUpscale(vec2 uv, vec2 motion, sampler2D current,
                        sampler2D history, sampler2D depth, float blend) {
    vec2 prevUv = uv - motion;
    vec3 h = texture(history, prevUv).rgb;
    vec3 c = texture(current, uv).rgb;

    // a neighbourhood clamp against ghosting
    vec3 lo = c, hi = c;
    for (int i = -1; i <= 1; ++i)
        for (int j = -1; j <= 1; ++j) {
            vec3 s = texture(current, uv + vec2(i, j) * texel).rgb;
            lo = min(lo, s); hi = max(hi, s);
        }
    h = clamp(h, lo, hi);

    float w = blend * (1.0 - smoothstep(0.01, 0.1, length(motion)));
    return mix(c, h, w);
}

Compute shaders: moving simulations to the GPU

Compute shaders: moving simulations to the GPU

A compute shader is a program that runs not as part of a draw but as a separate pass over a grid of data. It is ideal for tasks where millions of elements are processed identically: particles, physics, pathfinding, sorting, mesh generation.

compute shaderworkgroupdispatchbarrierGPGPU
01 Essence

The model is simple: the data lives in buffers, the shader is launched over N elements packed into workgroups of 64–256, and each invocation reads its data, computes and writes the result. The main difference from a vertex shader is that there is no geometry and no rasterisation — there is arbitrary memory access and the ability to read and write the same buffer (within one dispatch).

The limits of applicability are set not by “GPUs are faster” but by the data structure. If every element depends on its neighbours you need random access, atomics and sometimes a global barrier. If there is branching with a large spread in cost (noise, ray tracing), warp divergence eats the win: every thread in the group follows the most expensive branch. Good GPU tasks are “regular”: the same amount of work per element, sequential memory access, no branching.

Synchronisation inside a dispatch comes from barriers (memoryBarrier, workgroupBarrier, groupMemoryBarrier). A global barrier across the whole buffer only exists between dispatches — that is, between passes. Hence the rule: if you need “everyone computes, then everyone decides together”, that is two dispatches and two writes, not one with a global barrier. Data that travels between CPU and GPU needs pinned (mapped/coherent) flags and triple buffering, otherwise you get a stall.

the mathematical model
dispatch(x, y, z) → workgroups = ceil(N / group_size), total_threads = workgroups · group_size
group_size is usually 64 (AMD) or 128/256 (NVIDIA). Too small a group wastes time, too large hurts occupancy. Time ≈ N · cost_per_element / (GPU bandwidth).
02 How to build it
  1. Pick a task where the elements are independent: particles, cellular automata, grid search, morphology, convolution.
  2. Describe the input and output buffers; keep the data format dense (SoA, float32, no padded structs).
  3. Write the kernel: index = gid.x + gid.y·size.x; return early if the index is out of range.
  4. Choose the group size and the dispatch size; remember that dispatch is limited to 65535 on Y and Z.
  5. Split dependencies into separate dispatches; place barriers only where they are really needed.
  6. Verify against a CPU reference (float tolerance) — otherwise you are hunting races.

Millions of particles: GPU simulation and sorting

Millions of particles: GPU simulation and sorting

A 100 000-element particle system is not “many objects” but a dense array of data. On the GPU it is updated by a single dispatch and drawn with a single instanced call. The bottleneck is not the simulation but the sorting for transparency.

particlesbitonic sortindirect drawGPU particles
01 Essence

The CPU approach (a particle pool, a loop over it, sorting for alpha blending) hits three walls: updating the state, sorting, and issuing the draw. The GPU approach takes the first two off the CPU: the state lives in a buffer, a compute shader updates it, and the render reads the same buffer as instance attributes (position, colour, size). Sorting remains.

Sorting is only needed for correct alpha blending (back to front). On the GPU you use a bitonic sort: a merge sort that is parallel by nature, O(n·log²n). The standard trick is to sort 32-bit keys, where the high bits are the sort value (say depth) and the low bits are the particle index; the keys are sorted along with the data, then the data is permuted by the index. For 200 000 particles that is tens of milliseconds on the CPU — and milliseconds on the GPU.

Alternatives to sorting: (1) additive blending, where the order does not matter but correct transparency is lost; (2) weighted blended OIT, an approximate order-independent transparency that is the modern standard for sparks and smoke; (3) a two-pass render: opaque first, then transparent with depth fade. The conclusion: sort only where it actually changes the picture, otherwise use OIT.

the mathematical model
bitonic sort: O(n log²n) comparisons, particle_cost = sim + sort + draw
For 2^k elements: k(k+1)/2 passes. With 262 144 particles (2^18) that is 171 passes. Dropping to 2^16 removes a third of the sorting time.
02 How to build it
  1. Set the budget: how many particles fit into 1 ms of GPU. Start at 10 000 and measure.
  2. Keep the state in a single buffer (pos, vel, colour, life) in SoA or a dense struct layout.
  3. Update it with a compute shader: one dispatch per frame, no readback.
  4. If correct transparency is needed, sort keys (depth << 16 | index) with a bitonic sort.
  5. Draw with a single instanced call, reading the positions from the buffer instead of CPU structs.
  6. Cap overdraw: a million particles across the whole screen is a fill-rate problem, not a compute problem.

GPU-driven pipeline: GPU-side culling and command building

GPU-driven pipeline: GPU-side culling and command building

The classic frame: the CPU decides what is visible and issues a draw per group, the GPU draws. A GPU-driven pipeline flips the scheme: the GPU picks the visible objects and builds the command list, while the CPU issues a single call.

indirect drawGPU cullingHi-Zbindlesscompute pipeline
01 Essence

The problem with the classic scheme is that the CPU does not know what the GPU will finish in a frame, so planning is guesswork and the frame is bounded by the CPU. A GPU-driven pipeline solves it: the scene lives in permanent GPU buffers (positions, radii, mesh and material indices), a compute shader does the frustum culling and writes the surviving list into a buffer, and `drawElementsIndirect` / `drawIndirect` reads that buffer as the draw arguments.

Occlusion is done with a Hi-Z hierarchy: the previous frame's depth buffer is reduced into a pyramid (max-depth reduction), and an object's visibility is tested by sampling its AABB in the pyramid. The same buffer can be built before the main pass (depth prepass) to cull against the current depth.

The consequences and the price. Upside: the CPU barely participates in building the list, the frame becomes predictable, culling is more accurate. Downside: debugging is much harder, “draw calls” disappear from the profiler, and you have to think about synchronisation and about how to debug content. A separate problem is support: APIs like WebGPU expose the needed primitives, while WebGL2's indirect draw is only available through extensions.

the mathematical model
visible_list = cull(frustum, hzb) → count + instance_ids → drawIndirect(count)
One indirect draw per (mesh, material) instead of thousands of normal draws. CPU cost: 1 dispatch + 1 indirect draw per material group.
02 How to build it
  1. Move the scene into permanent GPU buffers: positions, radii, mesh and material indices.
  2. Write the culling compute shader: frustum test on the AABB, Hi-Z check, write the surviving indices.
  3. Group the visible objects by key (mesh + material) — that gives the counts for the indirect draws.
  4. Use drawIndirect / multi-draw with the counts from the GPU buffer.
  5. Drop per-draw state binding through bindless or texture arrays — otherwise every material still needs its own call.
  6. Add a debug mode: visualise the culled objects and the counters, or there is nothing to debug.

Async readback: avoiding GPU stalls

Async readback: avoiding GPU stalls

The fastest way to ruin the performance of a GPU game is to read a result back to the CPU in the same frame. That is a stall: the CPU waits for the GPU and the GPU waits for the CPU. The fix is asynchronous reading with a delay of one to three frames.

fencestallreadbacktriple bufferingPBO
01 Essence

How the problem works: a `map()` or `readPixels` on a buffer the GPU has not finished with makes the driver wait for the GPU to complete. During that wait the GPU cannot start the next frame and the CPU cannot start the next frame — both sit idle. The wait can be 5–50 ms, and all of it is wasted.

The solution is to separate them in time. The GPU writes into buffer A; the CPU sets a fence (a “I am done” signal) and on the next frame (or two) checks whether the signal fired. If it did, it reads the data from A (which no longer waits for the GPU) and starts the GPU working in buffer B. You end up with a pipeline: while the CPU processes generation N−2, the GPU computes generation N.

The details: triple buffering is needed because the GPU can be two or three frames ahead; a ring of buffers beats a single one. Data the GPU writes often but the CPU reads rarely should be packed (downsampling, aggregation on the GPU) — otherwise the bandwidth kills the whole benefit. And if the CPU needs the result in the same frame (for example, a cursor collision), you need a compromise: predict on the CPU, or accept the latency.

the mathematical model
stall = max(0, t_gpu_finish − t_cpu_request), pipelined_latency ≈ k · frame_time (k = 2…3)
A good sign: the readback costs < 0.2 ms of CPU and does not block the GPU. Triple buffering: buffers A/B/C, the CPU reads A while the GPU writes C.
02 How to build it
  1. Find every place where the CPU waits for the GPU: position readbacks, occlusion queries, picking, counter reads.
  2. Make the buffers asynchronous and attach a fence to each frame.
  3. Introduce a ring of two or three buffers: the CPU reads data that is one or two frames old.
  4. Reduce the volume: read only what you need (counters, the positions of selected objects), not the whole buffer.
  5. If the CPU needs a fresh result in the same frame, compute it in parallel on the CPU or predict it.
  6. Verify with a profiler: there should be no “GPU wait” in the frame.

using System.Collections.Generic;
using UnityEngine;
using UnityEngine.Rendering;

// Async readback: reading GPU data without waiting.
public class AsyncReader : MonoBehaviour
{
    const int Ring = 3;                       // a ring of buffers
    readonly ComputeBuffer[] _buffers = new ComputeBuffer[Ring];
    int _head = 0;                            // where we write now

    void OnEnable()
    {
        for (int i = 0; i < Ring; i++)
        {
            _buffers[i] = new ComputeBuffer(1024, sizeof(float) * 4,
                                           ComputeBufferType.Structured);
        }
    }

    // Call at the end of the frame: "capture the data once the GPU is done".
    public void Request()
    {
        _head = (_head + 1) % Ring;
        // the fence is set right after the dispatch: the signal means "the buffer is ready"
        GraphicsFence fence = Graphics.CreateGraphicsFence(
            GraphicsFenceType.AsyncQueueSynchronisation,
            SynchronisationStageFlags.ComputeProcessing);

        _pending.Add(new Pending { Buffer = _buffers[_head], Fence = fence });
    }

    struct Pending { public ComputeBuffer Buffer; public GraphicsFence Fence; }

    readonly List<Pending> _pending = new();

    void LateUpdate()
    {
        // Only take buffers whose fence has fired: waiting is not allowed
        for (int i = _pending.Count - 1; i >= 0; i--)
        {
            var p = _pending[i];
            if (!p.Fence.passed) continue;      // the GPU is not done yet - skip it
            var data = new float[1024];
            p.Buffer.GetData(data);             // the data is ready, this is not a stall
            _pending.RemoveAt(i);
        }
    }

    void OnDisable()
    {
        foreach (var b in _buffers) b?.Release();
    }
}

Procedural geometry on the GPU: marching cubes and SDF

Procedural geometry on the GPU: marching cubes and SDF

If the world is defined by a density field (SDF, noise, metaballs), you can turn it into polygons right on the GPU. That removes the heaviest phase — mesh building — from the CPU and opens the door to millions of triangles in real time.

marching cubesSDFisosurfacevoxelizationmesh generation
01 Essence

Marching cubes extracts an isosurface from a voxel grid: each cell has eight density values, their signs pick one of 256 intersection cases, and a table builds the polygon. On the CPU this is bounded by the number of cells: 256³ = 16.7 million cells is not a per-frame task. On the GPU every cell is a thread, and only the cells where the density crosses the isolevel have to be evaluated (you can reject blocks by their min/max).

The SDF approach (signed distance field) is simpler: the surface is the zero level of a distance function, and the geometry comes out of ray marching in a shader. That is implicit geometry: there is no mesh at all, only a function and a ray. Upsides: infinite detail, easy deformation (edit the field), trivial CSG. Downsides: expensive rendering (many samples per pixel) and no data for physics — so you often combine them: SDF for rendering plus a coarse grid for physics.

Another heavy class is SDF generation (neural models such as marching cubes over the voxels of a 3D generator). Here the GPU is used for (1) building the voxels, (2) marching cubes over them and (3) mesh compression. The practical rule: compute on the GPU only what is genuinely massive and parallel, and leave the final assembly (compression, LOD, collisions) to the CPU or to GPU passes that read back asynchronously.

the mathematical model
surfaces ≈ cells_touched, mesh_size ≈ 2.4 · cells_touched (triangles per cell on average)
Optimisation: first compute the min/max density of a 4×4×4 block and discard the whole block — that saves up to 90 % of the threads.
02 How to build it
  1. Define the field source: SDF, noise, metaballs or network voxels.
  2. Split the volume into blocks; for each block compute the min/max density.
  3. Run the compute shader over the cells: cells outside [min, max] are discarded.
  4. Use the 256-case table (or the 2D cases for marching squares) to generate the triangles.
  5. Compress the vertices on the GPU if the API allows, or weld them on the CPU after a readback.
  6. Build LOD and a BVH for physics: the raw mesh is far too heavy for collisions.

Physics and broadphase on the GPU

Physics and broadphase on the GPU

When there are thousands of objects, the physics bottlenecks are broadphase (who can hit whom) and the solver (iterations that resolve the contacts). Both parallelise well and have long moved to the GPU: broadphase through grid sorting, the solver through a compute shader.

broadphaseXPBDGPU physicscontact sortingsolver
01 Essence

GPU broadphase works like this: the positions of all bodies are written into a buffer, sorted by a spatial grid (or by Morton code), and candidate contacts are generated for each pair of neighbouring cells. The sort is the same bitonic sort used for particles. The alternative is a compute-based broadphase with a hierarchical BVH that is built or refitted on the GPU (Morton sort plus a tree built through references).

The solver on the GPU: each thread solves one contact, but contacts are coupled (friction pulls on neighbouring bodies), so data has to be exchanged between iterations — usually with atomics plus two buffers, or a Jacobi scheme where every contact reads the state at the start of the iteration. XPBD (position-based) suits the GPU particularly well: positions are written atomically or through a pull scheme, and stiffness does not depend on the iteration count.

Reality is that fully GPU-resident physics is rare: game logic, triggers, collisions with the player and “important” bodies usually stay on the CPU, while the GPU handles the mass (small debris, liquid). A workable architecture is hybrid: broadphase and part of the solver on the GPU, the important bodies on the CPU, and the result read back asynchronously (topic 61) and applied with a delay of one to two frames. The delay is hidden with interpolation.

the mathematical model
contacts ≈ Σ k_density · density², solve_time ≈ iterations · contacts · cost_per_contact
The rule: sorting (O(N log²N)) is cheaper than an O(N²) broadphase. Solver: fewer iterations at a larger time step is always a win.
02 How to build it
  1. Find the real bottleneck: broadphase, narrowphase or solver — measure them separately.
  2. Move the broadphase to the GPU: sort by grid (Morton) and generate the candidates.
  3. Solve the contacts in a compute shader with the Jacobi scheme: every contact reads the state at the start of the iteration.
  4. Use XPBD: stiffness is independent of the iteration count, so fewer iterations mean less traffic.
  5. Keep the “important” bodies on the CPU and synchronise via an async readback plus interpolation.
  6. Validate against a reference: GPU physics must converge to the CPU solution within tolerance.
03 Working code
GLSL 
#version 450
// XPBD contact solver on the GPU: one thread per contact.
layout(local_size_x = 64) in;

layout(std430, binding = 0) readonly  buffer Contacts { vec4 pairs[]; };   // (i, j, rest, stiffness)
layout(std430, binding = 1) buffer Positions { vec4 pos[]; };            // xy - position, zw - inverse mass
layout(std430, binding = 2) buffer Corrections { vec4 delta[]; };

uniform float dt;
uniform int contact_count;

void main() {
    uint i = gl_GlobalInvocationID.x;
    if (i >= uint(contact_count)) return;

    vec4 c = pairs[i];
    uint a = uint(c.x), b = uint(c.y);
    vec4 pa = pos[a];
    vec4 pb = pos[b];

    vec3 d = pb.xy - pa.xy;
    float len = length(d);
    if (len < 1e-6) return;

    vec3 n = d / len;
    float pen = c.z - len;                 // penetration
    if (pen <= 0.0) return;

    float wsum = pa.z + pb.z;
    if (wsum <= 0.0) return;

    // positional correction: dx = n * pen * (w_i / sum w) * stiffness
    vec3 corr = n * (pen * c.w * (pa.z / wsum));

    // Jacobi: both corrections go into a separate buffer and are summed on the next pass
    delta[a] += vec4(corr, 0.0);
    delta[b] -= vec4(corr, 0.0);
}

Heavy shaders: ray marching, volumetrics and SSR

Heavy shaders: ray marching, volumetrics and SSR

When a shader is expensive, it is not the code but the number of samples per pixel. Ray marching costs dozens to hundreds of samples per pixel, so what wins is not micro-optimisation but three tricks: a lower resolution, temporal reprojection, and noise instead of an exact result.

ray marchingvolumetricsSSRtemporal reprojectiondenoise
01 Essence

Three classes of expensive effect. Volumetrics integrate the density along a ray through a volume (fog, god rays): 20–64 samples per pixel multiplied by the number of lights. SSR (screen-space reflections) traces a reflected ray through the screen buffer with a binary search: 20–50 steps. Ray marching an SDF is similar: 50–150 samples. The common trait: the cost scales with the sample count, not with the complexity of the maths.

The first remedy is to render the effect at a lower resolution (half or quarter) and upscale it. The second is temporal reprojection: reuse last frame's result projected along the camera motion, and compute the new frame only in the regions of interest (where the pixel changed a lot). The third is to trace in a sparse way (stochastic sampling + blue noise + temporal accumulation) and then denoise.

Denoising is a mandatory part: sparse ray marching produces noise that is smoothed either spatially (a bilateral blur that respects depth and normals) or temporally (accumulation over a neighbourhood). “Cheap SSR with a blur-denoise” is often indistinguishable from exact SSR with 64 steps. The main rule: every expensive technique needs a degradation path — disable it, simplify it, or lower its update rate.

the mathematical model
cost ≈ pixels · samples · shader_cost, temporal_gain ≈ f_overlap (0.5…0.95)
Half res gives a 4× fill-rate saving, quarter res 16×. Reprojection gains more the more of the screen is covered (f_overlap).
02 How to build it
  1. Measure the fill rate: how many samples per pixel your shader takes and what that costs in milliseconds.
  2. Move the effect to half resolution, add bilinear upscaling and dithering to remove banding.
  3. Enable temporal reprojection: keep the previous result and the camera motion matrix.
  4. Replace the deterministic traversal with a stochastic one (blue noise) and add denoising.
  5. Cap the effect's influence: a maximum number of samples per frame and automatic degradation under load.
  6. Provide a switch: on weak hardware the effect is disabled or simplified, not left to eat the frame.

#version 450
// Ray tracing through an SDF with an early exit and gradient stepping.
float sdf(vec3 p) {
    // a "bubble" structure: a cheap analytic function
    p = abs(p);
    return length(p) - 1.0 + 0.25 * sin(3.0 * p.x) * sin(3.0 * p.y) * sin(3.0 * p.z);
}

vec3 sdfNormal(vec3 p) {
    const vec2 e = vec2(1.0, -1.0) * 0.0015;
    return normalize(
        e.xyy * sdf(p + e.xyy) + e.yyx * sdf(p + e.yyx) +
        e.yxy * sdf(p + e.yxy) + e.xxx * sdf(p + e.xxx));
}

bool raymarch(vec3 ro, vec3 rd, out float t, int max_steps) {
    float dist = 0.0;
    t = 0.0;
    for (int i = 0; i < max_steps; ++i) {
        vec3 p = ro + rd * dist;
        float d = sdf(p);
        if (d < 0.001) return true;          // hit the surface
        dist += d;                           // step along the SDF
        if (dist > 40.0) break;              // left the scene bounds
    }
    return false;
}

GPU profiling: timestamps, counters and occlusion queries

GPU profiling: timestamps, counters and occlusion queries

On the CPU you see how long a frame took; on the GPU you see how long a specific pass took. Tools give you that through timestamp queries, pipeline counters and occlusion queries. Without them, GPU optimisation is guessing from one overall timer.

timestamp queryGPU counterRenderDococclusion querypipeline statistics
01 Essence

A timestamp query asks the GPU for the time between two moments. Usually one per pass (scene, shadow, test, post) or one per frame; the result arrives one or two frames later, so you accumulate them and read them asynchronously (topic 61). The names differ per API (VK_EXT_calibrated_timestamps, D3D12 queries, Nsight) but the meaning is the same.

Pipeline counters give you what the time alone cannot: how many triangles, shader invocations, state switches, stalls, occlusions and full-screen quads. They are what turns “the time went into rendering” into “5000 draw calls and 12 million triangles”. Profilers (RenderDoc, PIX, Nsight Graphics, Xcode) can count them for you.

Occlusion queries are a stress test for the culling: how many pixels did the object actually write into the depth buffer? Zero means it is fully hidden and can be skipped. The query is asynchronous and the result arrives several frames later, so the decision is made with a delay (see topic 33). The occlusion depth is useful too: how many layers cover it — that decides whether an LOD is needed.

the mathematical model
pass_time = Σ timestamps, efficiency = useful_pixels / shaded_pixels
The useful metric is not “the pass took 3 ms” but “how much work it did per millisecond”: a shader that shades 10 % of the screen and costs 4 ms is expensive.
02 How to build it
  1. Enable timestamps per pass: scene, shadows, test, post, UI.
  2. Count the key metrics: draw calls, triangles, shader invocations, state changes.
  3. Compare the “worked screen” (shaded pixels) with the “useful screen”: a ratio below 50 % is an optimisation candidate.
  4. Add occlusion queries for large objects and measure how much is really visible.
  5. Look at p95/p99 across frames, not the average: one heavy pass in 30 % of frames ruins everything.
  6. Compare against a reference: “the pass took 3 ms” means nothing without “at 1080p/4K, with N particles”.
03 Working code

class GpuProfiler:
    """Accounting of the passes via timestamp queries and counters."""
    def __init__(self):
        self.passes = {}          # name -> list of durations
        self.counters = {}        # name -> value

    def begin_pass(self, name):
        self._t0 = time.perf_counter()   # a real API uses a timestamp query here

    def end_pass(self, name):
        dt = (time.perf_counter() - self._t0) * 1000.0
        self.passes.setdefault(name, []).append(dt)

    def set_counter(self, name, value):
        self.counters[name] = value

    def report(self, budget_ms=16.6):
        rows = []
        for name, vals in sorted(self.passes.items()):
            vals = sorted(vals)
            p95 = vals[min(len(vals) - 1, int(len(vals) * 0.95))]
            rows.append((name, round(sum(vals) / len(vals), 2), round(p95, 2)))
        rows.sort(key=lambda r: -r[2])
        over = [(n, p95) for n, _, p95 in rows if p95 > budget_ms]
        return {
            "passes": rows,
            "over_budget": over,
            "counters": self.counters,
            "gpu_total": round(sum(r[2] for r in rows), 2),
        }

Quality scaling and graceful degradation

Quality scaling and graceful degradation

The same content has to run on a powerful PC and on a laptop with integrated graphics. So quality is not a fixed setting but a set of levers that the engine moves according to the frame budget: resolution, LOD distance, number of effects, shadow quality.

scalabilitydynamic resolutionLOD biasfallbacktier
01 Essence

The architecture of degradation is a set of independent “levers” plus a controller that picks their values from the current performance. Levers: render scale (0.5–1.0), LOD bias, the number of dynamic shadow casters, post-processing quality, the particle budget, the draw distance, texture resolution (streaming), audio quality. The controller measures the p95 frame time and changes the parameters smoothly, never in a jump.

Dynamic resolution is the most effective lever: you render at a lower resolution and upscale. There are two strategies: “render time is fixed” (drop the resolution to fit the budget) and “resolution is fixed” (drop the quality of the effects). The first preserves responsiveness, the second preserves sharpness; in practice you combine them and add hysteresis so the resolution does not “breathe”.

More important than the exact values is the absence of “steps”: if the player notices the switch, they will read it as lag. So the transitions are gradual (LOD fades, shadow cross-fades, the resolution does not jump), decisions are made on a smoothed metric rather than a single frame, and the settings do not oscillate. At startup the engine detects the device class (memory, GPU, resolution) and picks a baseline set, then adapts at runtime.

the mathematical model
scale = clamp(target_ms / measured_ms, min_scale, 1.0) — smoothed: scale ← lerp(scale, new_scale, 0.05)
Degradation order: resolution first, then LOD distance, then shadows, then effects, then audio quality. Start with what the player notices least.
02 How to build it
  1. Define the target device class by memory, GPU and screen resolution.
  2. Split the quality settings into “visual” (shadows, particles) and “performance” (resolution, LOD distance, light count).
  3. Make the controller work on the p95 frame time with slow adaptation (a few seconds) and hysteresis.
  4. Add smooth transitions: fades between LODs, cross-faded shadows, no jumping resolution.
  5. Allow a manual override: an auto mode plus a few presets (low / medium / high / ultra).
  6. Collect telemetry per device: real profiles beat any assumption.

        self.lod_bias = 0.0        # +1 = further LODs
        self.shadow_quality = 1.0  # 0..1
        self._ema = target_ms

    def update(self, frame_ms):
        # a smoothed metric: one heavy frame must not drop the quality
        self._ema += (frame_ms - self._ema) * 0.05
        if self._ema > self.target:
            # resolution first (the least noticeable), then everything else
            self.scale = max(self.min_scale, self.scale - 0.02)
            self._ema = self.target  # keep the metric from running away while we adapt
        elif self._ema < self.target * 0.85:
            self.scale = min(1.0, self.scale + 0.01)
        return self.settings()

    def settings(self):
        return {
            "render_scale": round(self.scale, 2),
            "lod_bias": round(self.lod_bias, 2),
            "shadow_quality": round(self.shadow_quality, 2),
        }

# A degradation order that does not break the feel:
# 1) render scale 1.0 -> 0.6 (noticeably softer)
# 2) shadows: number of casters and map resolution
# 3) LOD distance / culling
# 4) particle volume and post effects
# 5) audio quality and voice count

Time
O(1) per frame for the controller
Memory
O(1)
In practice
The rule: degradation must be invisible in motion — otherwise it is worse than a stable low setting.
05 Where people usually get it wrong
  • Changing quality instantly: the switch is visible and the player reads it as a frame-rate drop.
  • Dropping the resolution below 0.6: the blur is worse than missing shadows.
  • Automation without a manual override: every player has their own taste and the auto mode has to yield.
  • Adding a new lever in the middle of the project: testing the matrix of “content × setting” is expensive.
  • Optimising only for the “average” PC: real users are the tail of the devices, not the middle.

Glossary of terms

37 terms

Terms that show up both in this text and in job descriptions. Keep them handy during a technical interview.

A*
Shortest-path search with a heuristic h(n): f(n) = g(n) + h(n). An admissible heuristic never overestimates the remaining cost.
ECS
Entity Component System: entity — an id, components — data, systems — logic. Gives cache locality and composition.
DOD
Data-Oriented Design: lay out memory for the traversal first, code second. The base of fast simulations.
Fixed-point
Fixed-point arithmetic (Q16.16): deterministic across platforms, unlike float.
Lockstep
Clients exchange only commands and simulate the same world; state is never transmitted.
Rollback
Resimulating unconfirmed inputs from a server snapshot; the basis of client-side prediction.
Verlet
Position-based integration: x′ = 2x − x_prev + a·dt². Stable, convenient for constraints.
PBD / XPBD
Position-Based Dynamics: constraints are projected onto positions; XPBD makes stiffness iteration-independent.
SPH
Smoothed Particle Hydrodynamics: a fluid as particles with a smoothing kernel and pressure.
BVH
Bounding Volume Hierarchy: an AABB tree for fast culling and raycasts; built with SAH.
SAH
Surface Area Heuristic: a BVH split quality criterion based on bounding surface area.
MCTS / UCT
Monte Carlo Tree Search with the UCT rule: balancing exploration and exploitation in a game tree.
Utility AI
Choosing an action by a weighted sum of normalised factors; an alternative to behaviour trees.
Flow field
A grid of directions towards a goal: cheap pathing for large groups of units.
WFC
Wave Function Collapse: constraint-based generation with propagation and backtracking.
SDF
Signed Distance Field: distance to a surface; convenient for CSG and ray marching.
Marching cubes
Extracting an isosurface from a density grid using a 256-case table.
PBR / BRDF
Physically Based Rendering: energy-conserving materials; the BRDF describes light reflection.
GGX
Microfacet normal distribution model with a long specular tail.
Ambisonics
Encoding 3D audio in spherical harmonics (W, X, Y, Z) and decoding it for headphones or speakers.
HRTF
Head-Related Transfer Function: the filter describing how ears and head colour sound from a direction.
PRD
Pseudo-Random Distribution: the chance grows after failures, reducing streak variance without changing the mean.
Glicko-2 / TrueSkill
Bayesian ratings with uncertainty (RD/σ) updated after a match.
ARIMA
Time-series model: autoregression, differencing and a moving average of errors.
GAN
Generator versus discriminator; WGAN-GP stabilises training via the Wasserstein distance.
FFT
Fast Fourier Transform: O(N log N); used for oceans, texturing and audio.
Perlin / fBm
Gradient noise and its fractal sum of octaves; the base of procedural terrain and materials.
Kepler
T² = 4π²a³/(G(M+m)); the equation M = E − e·sin E links time and position on the orbit.
Draw call
A draw submission: one batch of geometry with one pipeline state. The main unit of CPU render cost.
Compute shader
A program executed as a separate pass over a grid of data; not bound to geometry.
Workgroup
A group of GPU threads working together; a barrier inside the group is nearly free.
Stall
A wait where the CPU or the GPU sits idle waiting for the other. The main enemy of asynchrony.
Hi-Z
A max-depth reduction pyramid of the previous frame; a cheap source of occlusion tests.
False sharing
Two threads write to different fields of one cache line and keep invalidating it for each other.
Temporal reprojection
Reusing last frame's result reprojected along camera motion.
OIT
Order-Independent Transparency: transparency without sorting, via weighted accumulation and division.
A/B test
Comparing two variants on random player cohorts: the only honest way to verify an effect.

Method and limits

Formulas use game units rather than SI where that reads better; constants are tuned for gameplay, not for a physics lab. The code is minimal, without optimisations or error handling: its job is to show the structure, not to replace an engine. Complexity figures assume a typical implementation; real numbers depend on platform and compiler.

The demos use Canvas 2D and plain maths: no libraries, no CDN, no build step. That is deliberate — the file opens with a double click, works offline and never goes stale with its dependencies.
